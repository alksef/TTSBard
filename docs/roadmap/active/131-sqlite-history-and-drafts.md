# ROADMAP-131 — Новое хранение истории, подсказок и черновиков

## Цель

Перенести историю фраз, словарь подсказок, сочетания слов и вкладки с
черновиками из JSON в SQLite. Снять ограничение хранения 200 фраз, сохранить
поиск и воспроизведение всей доступной истории, загружать список порциями.
При изменениях записывать затронутые данные, а не весь накопленный набор.
Переход и пользовательские изменения входят в одно направление и один релиз;
реализация разбивается на проверяемые локальные задачи.

Пользователь согласовал направление SQLite, включение вкладок и отсутствие
лимита хранения истории. Детали ниже — проект решения, а не уже реализованная
архитектура. Производительность ещё не измерена.

## Исходное состояние

- `src-tauri/src/history.rs`: все слова, n-граммы и фразы загружаются в память.
  Запись текста целиком сериализует `input_history.json` и `ngrams.json`,
  последовательно атомарно заменяет файлы с отдельным `sync_all` для каждого.
  Единой транзакции двух файлов нет. Фразы аналогично сохраняются целиком.
- Фразы ограничены 200 записями; `PhraseHistoryList.vue` запрашивает 100;
  `replay_phrase_from_cache` ищет ID только среди первых 200.
- `useEditorTabs.ts` объединяет изменения задержкой 500 мс и последовательно
  отправляет снимки всех вкладок; `tabs.rs` сохраняет весь `tabs.json`.
  `flushSave` вызывается в существующих сценариях закрытия/размонтирования.
- Аудио хранится отдельно: запись истории содержит `cache_key`, по которому
  читается конкретный WAV. Перебора каталога для воспроизведения нет.
- Действующее [DECISION-008](../../decisions/008-json-persistence.md) предписывает
  JSON; [ROADMAP-013](../rejected/013-history-storage-json-vs-sqlite.md) ранее
  отклонил SQLite при малых объёмах. Перед реализацией оформить утверждённое
  исключение для истории и черновиков и связать документы. Старое решение
  остаётся применимым к конфигурации.

## Границы

Перенести `phrase_history.json`, `input_history.json`, `ngrams.json`, `tabs.json`
в отдельные таблицы одной базы. Сохранить ID, счётчики, даты, тексты, метаданные
голосов и кеша, названия/порядок/активную вкладку, route и purpose.

Оставить JSON для `settings.json`, `windows.json`, `soundpanel_bindings.json`,
`intercept.json` и каталога ElevenLabs. Исправление атомарности intercept —
независимая работа. Не менять синтез, аудиоформат, обработку текста, интеграции
и правила очистки аудиокеша. WAV не переносить в БД.

Отсутствие лимита означает отсутствие автоматического вытеснения фраз по
числу записей. Размер страницы и ограничение IPC-запроса остаются. Существующие
ограничения числа вкладок и размера черновика не отменять автоматически:
это отдельное продуктовое решение; миграция не должна молча обрезать данные.
Не вводить автоматическое удаление обученных слов/n-грамм в рамках перехода.

## Предлагаемый технический подход

- Встраиваемая SQLite; кандидат — `rusqlite` с `bundled`, без серверной БД и ORM.
  Предпочтительный async bridge — `tokio-rusqlite`; сначала проверить совместимые
  версии, локальный Rust toolchain/MSRV и поставляемую SQLite. Не подключать
  параллельно разные несовместимые версии `libsqlite3-sys`.
- Один сервис-владелец соединения в отдельном рабочем потоке, async API наружу;
  не выполнять блокирующий SQL в async executor или UI. Подтверждать сохранение
  после commit. Ограничить накопление очереди, объединять устаревшие сохранения
  вкладок без потери последнего состояния. Дополнительное чтение/кеш — по замерам.
- Таблицы `phrases`, `words`, `bigrams`, `trigrams`, `tabs`, состояние редактора
  и служебные метаданные. Индексы ID, порядка истории, контекстов n-грамм.
  Параметризованные запросы и повторно используемые statements.
- Агрегировать повторяющиеся токены текущего текста; обновлять слова и n-граммы
  через UPSERT одной транзакцией. Не делать commit на каждое слово.
- Для вкладок изменять только отличающиеся строки/поля и порядок/active ID.
  Допустимо сначала сравнивать входной снимок в сервисе, но нельзя переносить
  прежнюю полную перезапись в DELETE-all/INSERT-all. Очистка истории не затрагивает
  вкладки. Сохранять существующую защиту от запоздалых ответов и порядок записей.
- Нумерованные SQL-миграции схемы в транзакциях; `PRAGMA user_version` для версии,
  отдельная отметка импорта JSON. Специальная библиотека миграций необязательна.
- Для локального пути кандидат — WAL с `synchronous=FULL`, короткими транзакциями,
  `busy_timeout` и контролем checkpoint. NORMAL допускается лишь после отдельного
  согласования потери последних commit при сбое питания. Не использовать OFF.
- До реализации утвердить путь базы. Исходники находятся в Roaming config;
  предпочтение для WAL — локальный каталог пользовательских данных. База с
  черновиками не является регенерируемым кешем. Учесть `storage.data_dir`,
  перенос/резервирование, сетевые или redirected Roaming-пути; WAL не подходит
  для network filesystem. Нельзя незаметно изменить семантику хранения/переноса.
- Бэкап живой базы выполнять SQLite backup API; копирование одного основного
  файла при активном WAL недостаточно. Не расширять scope до нового UI бэкапов.

## Миграция JSON при запуске

1. После single-instance, до доступа истории/редактора открыть базу и применить
   поддерживаемые миграции схемы. Новую неизвестную версию не сбрасывать.
2. Проверить служебную отметку импорта. `settings.json` не является источником
   истины о завершении импорта; наличие файла базы само по себе тоже недостаточно.
3. Прочитать четыре JSON с поддержкой действующих legacy-форматов. Отсутствующий
   файл на новой установке — нормальный случай; повреждённый существующий файл
   не считать пустым. Выдать понятную ошибку с сохранением исходных данных.
4. В одной транзакции импортировать все данные и поставить отметку завершения.
   Сохранить UUID и кеш-ключи, оба представления текста, Unicode, порядок вкладок.
   Учесть нынешнюю дедупликацию с метаданными/без них: простой UNIQUE по тексту
   может изменить поведение. Проверять конфликтующие ID и входные данные.
5. При ошибке откатить импорт. Повтор не создаёт дубликаты и не увеличивает count.
   После commit использовать только БД, без двойной записи и повторного импорта.
6. Исходные JSON оставить неизменными резервными копиями. После успешного импорта
   очистка истории или перезапуск не должны возвращать старые записи из этих копий.
   Удаление/утрата базы — отдельный сценарий восстановления, без тихого импорта
   устаревших исходников как актуального состояния. Старые версии приложения
   будут видеть старый снимок JSON: документировать ограничение downgrade.

Для небольших данных перенос автоматический, без обязательного подтверждения.
Показывать нейтральный статус только если операция заметно затянулась;
ошибку — явно с возможностью повторить. Не обещать восстановление фраз,
уже вытесненных прежним лимитом 200.

## История, поиск и черновики

- Удалить автоматическое вытеснение 200 фраз. Сохранить действующие правила
  дедупликации и count: это не введение отдельного журнала каждого воспроизведения.
- Список порциями, ориентир 100 строк, со стабильным порядком `(last_used, id)`
  и курсором. При изменении фильтра/добавлении/удалении сбрасывать либо согласованно
  обновлять страницы; учитывать устаревшие ответы, одинаковые даты, загрузку,
  ошибку и конец списка. Не выгружать всю историю в frontend ради поиска.
- Поиск по всей базе с сохранением case-insensitive substring для русского
  и английского, буквальных `%`, `_` и спецсимволов. Нормализацию сохранить в Rust;
  встроенного NOCASE недостаточно для русского. Обычный B-tree не ускоряет
  произвольную подстроку. FTS5 trigram — кандидат по результатам замеров, с
  fallback для 1–2 символов и финальной проверкой совпадений. Символьный trigram
  индекс поиска отличается от обучающих сочетаний трёх слов.
- Replay ищет одну фразу по ID, читает прежний WAV по `cache_key`.
  История может существовать дольше аудиофайла: оставить корректный CacheMiss.
- Черновики автоматически сохраняются после короткой паузы; одинаковое состояние
  не записывается. При штатном закрытии дождаться commit последнего состояния;
  при ошибке сохранения не закрывать без объяснения риска потери текста.
  При аварии гарантируется последнее успешно сохранённое состояние, а не текст,
  ещё ожидающий debounce. Проверить реальное native-закрытие, а не только unmount.

## Этапы одного направления

1. Утвердить путь/ownership, библиотеку и долговечность; зафиксировать исходные
   контракты и benchmark JSON. Создать небольшой Rust-прототип SQL на синтетике.
2. Добавить сервис, схему и автоматический идемпотентный импорт четырёх JSON.
3. Перевести запись/чтение истории, слов и n-грамм; replay по ID, убрать retention.
4. Перевести сохранение/восстановление вкладок на адресные изменения и проверить
   очередь, ошибки и graceful shutdown.
5. Добавить порционную загрузку истории и поиск по всему набору, локализацию
   нужных состояний. Следовать UI map/guidelines, обновлять карту при изменении
   состава поверхностей.
6. Независимо проверить миграцию, сбои, конкуренцию и производительность;
   обновить архитектуру/решение/пользовательские ограничения и принять релиз.

Это существенный локальный рефакторинг хранения с изменением backend API и списка
истории, не переписывание TTS или приложения. Ориентир 6–9 небольших implementation
tasks с отдельными критериями; календарная оценка после прототипа. DeepSeek
реализует задачи по [AI workflow](../../development/ai-workflow.md), Codex
проверяет код и результаты. Временные baseline/tasks/reviews/логи/скриншоты —
только `.work/ai/<work-id>/`, путь отчёта UI указывается в конкретном task.

## Приёмка и измерения

- Перенос полной/частичной по наличию файлов/пустой установки; legacy, Unicode,
  повреждение, отказ записи, прерывание процесса, повтор и неизвестная версия.
  Нет потери, двойного импорта и молчаливого создания пустой истории.
- Фразы за пределами прежних 100/200 доступны в списке, поиске и replay;
  страницы не дублируются при обычной навигации, устаревшие ответы игнорируются.
- Слова, n-граммы, дедупликация и ранжирование сохраняют контракты; сбой транзакции
  не публикует частично обновлённые данные.
- Несколько вкладок, активная/порядок/route/purpose, быстрый набор/смена/удаление,
  штатное закрытие и восстановление после crash; ошибка сохранения видна.
- Сравнить JSON/SQL на одном диске и release-конфигурации, при одинаковой
  durability: p50/p95/p99 save/query/startup, память, disk size, записи включая
  WAL/checkpoint. 200/5000/50000 фраз, 1500/10000/100000 слов,
  10000/100000/1000000 n-грамм; несколько больших черновиков. Поиск 1/2/3+
  символов, warm/cold, одновременные запросы и autosave. До измерения не обещать
  конкретного ускорения; чтение из прежнего HashMap может быть быстрее SQL.
- Нет полной перезаписи набора при повторе фразы/изменении одной вкладки;
  память/размер IPC-ответов списка ограничены страницей, а не всей историей.
- Rust-проверки через `scripts/cargo.ps1`, debug/release build через
  `scripts/build.ps1`; релевантные frontend tests и UI/native-проверка.

## Первичные источники и вывод для Rust

Проверены 2026-10-08. SQLite прямо описывает свой формат как хранилище данных
приложения; для истории/черновиков подход соответствует назначению механизма.

- [SQLite application file format](https://www.sqlite.org/appfileformat.html).
- [WAL](https://www.sqlite.org/wal.html): страницы, checkpoint, один writer,
  локальный filesystem; выбирать версию с исправлением WAL-reset (3.51.3+
  либо документированный backport), проверить фактический bundled runtime.
- [Backup API](https://www.sqlite.org/backup.html),
  [synchronous и user_version](https://www.sqlite.org/pragma.html),
  [FTS5](https://www.sqlite.org/fts5.html),
  [Unicode FAQ](https://www.sqlite.org/faq.html).
- [rusqlite](https://github.com/rusqlite/rusqlite): bundled для Windows;
  [Connection](https://docs.rs/rusqlite/latest/rusqlite/struct.Connection.html)
  имеет Send, но не Sync. Shared connection требует контролируемого доступа.
- [tokio-rusqlite](https://docs.rs/tokio-rusqlite/latest/tokio_rusqlite/):
  рабочий поток на соединение, запросы/результаты через каналы. Это готовый
  вариант async bridge, не требуется писать свой механизм только ради SQLite.
- [SQLx SQLite](https://docs.rs/sqlx/latest/sqlx/sqlite/struct.SqliteConnection.html)
  также использует background thread. Полноценная альтернатива, если нужны его
  async/query/migration возможности; для текущего узкого scope предпочтителен
  rusqlite. SQLite не становится неблокирующей только из-за async Rust API.
