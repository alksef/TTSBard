# ROADMAP-049 — Надёжная корреляция ответов Silero

## Проблема

Silero TTS отправляет текст в `@silero_voice_bot`, но текущий путь синтеза не
сохраняет идентификатор отправленного сообщения. Ожидание завершает первое
подходящее обновление с `audio/mpeg` или `audio/ogg` без проверки диалога и
связи с конкретным запросом. Один общий Telegram update receiver также
используется запросами голоса, лимитов и смены спикера.

В результате ответы могут быть пропущены, перехвачены другим потребителем или
ошибочно отнесены к текущему запросу. Пользователь видит случайные ошибки при
том, что бот уже создал корректный MP3.

## Целевое поведение

- аудио принимается только из личного диалога с `@silero_voice_bot`;
- ответ относится к конкретному исходящему сообщению, а не к любому следующему
  аудиообновлению;
- посторонние и устаревшие обновления игнорируются и не завершают ожидание;
- скачанный файл получает уникальный путь, проверяется до передачи декодеру и
  не читается во время записи;
- timeout и отброшенные кандидаты диагностируются без логирования текста,
  токенов и других секретов.

## Этапы

### P0 — Корреляция TTS-запроса

1. Возвращать ID из `send_text_to_bot` и передавать его в ожидание ответа.
2. Проверять входящее сообщение по направлению, peer Silero и связи с ID
   исходящего сообщения; принимать аудио только с явным `reply_to`, равным ID
   текущего TTS-запроса.
3. Покрыть чистую логику отбора тестами: чужой peer, исходящее сообщение,
   старое аудио, неверный `reply_to`, корректный MP3/OGG.

### P1 — Единый маршрутизатор Telegram updates

1. Заменить конкурирующее чтение одного receiver диспетчером с подписчиками или
   pending-request registry.
2. Изолировать ответы `/speaker`, `/limits`, смены голоса и синтеза.
3. Определить поведение при disconnect, timeout и позднем ответе.

### P2 — Лимиты Silero в UI

Backend-команда `telegram_get_limits`, состояние `limits` и метод
`refreshLimits()` уже существуют, но UI их не вызывает и не отображает.

1. Расширить `Limits` временем следующего обновления: ответ бота содержит строку
   вида `17 / 666 обновится 07-27 00:47:27 UTC+3`, а текущий парсер сохраняет
   только счётчики `voices` и `gifs`.
2. Рекомендуемый вариант — компактная строка над списком голосов в карточке
   Silero: `Символы: 17 / 666 · обновится 27.07 в 02:47` и icon-only refresh с
   `title`/`aria-label`. Время показывать в локальной зоне пользователя, а
   исходное значение и зону бота — в tooltip.
3. Альтернативы для сравнения перед реализацией:
   - две небольшие метрики `Символы` и `Кружки/гифки`, общее время обновления
     отдельной строкой — нагляднее, но занимает больше высоты;
   - только кнопка `Лимиты` с popover — компактнее, но состояние не видно без
     дополнительного действия.
4. Загружать лимиты один раз при подключении/восстановлении Telegram-сессии и
   после успешного явного reconnect; затем обновлять только вручную. Раскрытие
   карточки и озвучка не отправляют `/limits`. Предусмотреть loading, stale value
   и локальную ошибку, не заменяющую статус Telegram-соединения.
5. Покрыть парсер времени, composable stale/error behavior и отображение узкими
   тестами.

### P3 — Целостность загрузки и диагностика

1. Использовать UUID либо ID Telegram-сообщения в имени временного файла.
2. Скачивать во временный `.part`, проверять непустой размер и аудиосигнатуру,
   затем атомарно публиковать готовый файл.
3. Добавить структурированные поля request/message ID, MIME и размера файла;
   текст сообщения в лог не включать.

## Проверка

- targeted unit-тесты `telegram::bot`;
- `cargo test --lib`;
- `cargo check --manifest-path src-tauri/Cargo.toml`;
- ручной сценарий: серия одинаковых фраз, постороннее Telegram-аудио во время

## Условия завершения

- P0 реализован и подтверждён тестами;
- постороннее либо устаревшее аудио не может быть выбрано как результат TTS;
- оставшиеся P1/P2/P3 риски либо реализованы, либо явно сохранены как следующие
  этапы roadmap.

## Статус реализации

P0 реализован 2026-07-25: путь синтеза сохраняет ID исходящего сообщения и ID
peer Silero, после чего фильтрует кандидаты по направлению, peer, порядку ID,
явному `reply_to` и MIME. Добавлены unit-тесты чистых правил сопоставления.

Ручной прогон 2026-07-26 подтвердил для трёх последовательных запросов, что
Silero возвращает MP3 с явным `reply_to`, точно равным ID исходящего сообщения.
Параллельная отправка из трёх вкладок также успешно прошла пользовательскую
проверку. Ответы без `reply_to` после этого наблюдения отклоняются.

P1 подготовлен 2026-07-26: raw Telegram receiver принадлежит одной фоновой
задаче, которая рассылает обновления независимым bounded broadcast-подписчикам.
TTS, чтение текущего голоса, `/limits` и смена спикера подписываются до отправки
команды, поэтому больше не забирают обновления друг у друга. Ответы с
`reply_to` проверяются по peer, направлению, порядку ID и исходящему request ID.
Replyless `/limits` дополнительно сериализован и принимается только от Silero,
после ID команды и при совпадении формата ответа. Disconnect закрывает текущую
рассылку, broadcast lag завершает ожидание явной ошибкой.

Компиляция подтверждена `cargo check` и `cargo test --no-run`. Запуск тестового
бинарника в текущем Windows-окружении блокирует ошибка загрузки нативной DLL
`STATUS_ENTRYPOINT_NOT_FOUND`; P1 требует ручной проверки одновременных TTS и
`/limits`, disconnect и timeout. Поздний replyless-ответ `/limits` после timeout
остаётся неоднозначным ограничением протокола и требует отдельного решения.
P2 реализован 2026-07-26: парсер сохраняет необязательное время обновления,
карточка Silero показывает расход символов и локализованное время, а исходную
зону и лимит кружков/гифок оставляет в tooltip. `/limits` автоматически
запрашивается только при подключении, восстановлении сессии или успешном
reconnect; дальнейшее обновление выполняется кнопкой. Ошибка лимитов локальна,
предыдущее значение сохраняется как stale. P3 (целостность загрузки) остаётся
следующим этапом.
