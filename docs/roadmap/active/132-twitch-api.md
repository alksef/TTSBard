# ROADMAP-132 — Режим отправки через Twitch API

## Цель и статус

Добавить в существующую панель Twitch выбор обычной IRC-отправки или
отправки сообщений TTS через Twitch Helix API. Сохранить текущую настройку и поведение IRC по умолчанию.

2026-10-09 пользователь разрешил реализацию с отдельной авторизацией владельца
канала и без прав модератора. Работа ведётся узкими задачами DeepSeek через
OpenCode с независимым review. Локальная схема с личным Confidential-приложением
требует проверки прототипом и ручной отправкой в Twitch.

Первый этап ограничен одним личным каналом, авторизацией обоих аккаунтов на
том же компьютере; API и OAuth реализуются через библиотеки twitch-rs.

2026-10-10 пользователь подтвердил название режима «Twitch API» и сохранение переключения IRC/API.

Текущее состояние реализации:
- `twitch::auth`: координатор `TwitchAuthCoordinator` с DPAPI-хранилищем, сериализацией модификаций через generation counter, валидацией токенов при простое и ротацией refresh-токена.
- Порядок инициализации (composition root): координатор авторизации публикуется в `AppState` до запуска supervisor'а Twitch.
- Tauri IPC команды: `get_twitch_api_auth_status`, `save_twitch_api_client`, `begin_twitch_api_auth`, `finish_twitch_api_auth`, `cancel_twitch_api_auth`, `clear_twitch_api_auth`.
- Настройки и рантайм: режим `TwitchMode` (`irc` | `api`, по умолчанию `irc`), поддержка обоих транспортов в `TwitchClient`, разбиение на части до 500 Unicode-символов для Helix API, классификация терминальных/повторяемых ошибок, валидация сессии при простое и предотвращение дублирования хвоста длинных фраз при ошибке.
- Frontend: композибл `useTwitchApiAuth`, обновление `useTwitch`, панель `TwitchPanel.vue` с выбором режима, настройкой Client ID/Secret, копируемым Redirect URL, карточками авторизации бота и стримера, отменой и сбросом доступов.
- Локализация: паритет RU/EN ключей в `locales/ru.json`, `locales/en.json` и `src-tauri/locales/en.json`.
- Автотесты: unit- и интеграционные тесты Twitch (auth, client, limits, setup, servers), тесты IPC-команд, vitest тесты frontend, проверка контрактов IPC, паритет настроек и локалей.

Roadmap остаётся `in_progress` до завершения независимой матрицы ручных сценариев пользователем в реальном Twitch.

## Исходное состояние

`src-tauri/src/twitch/client.rs` использует `twitch-irc`, подтверждение JOIN,
ограниченную очередь и последовательную отправку. Команды отправки находятся
в `src-tauri/src/commands/twitch.rs`; разбиение текста в `twitch/limits.rs`
учитывает IRC-пакет. `TwitchPanel.vue` и `useTwitch.ts` предоставляют настройку
логина, токена и канала, статусы, автозапуск и тестовое сообщение.

## Первый этап — исходный объём

- Два режима в текущей панели: «Обычный (IRC)» и «Twitch API».
  Существующие настройки без нового поля режима продолжают работать через IRC.
- API-режим использует личное Twitch-приложение пользователя: Client ID
  и Client Secret. Общий секрет не включается в распространяемую сборку.
- Twitch API и операции OAuth делегировать `twitch_api` и `twitch_oauth2`.
  Это сторонние открытые библиотеки twitch-rs, не официальный SDK Twitch.
  Собственными остаются loopback callback, хранение, lifecycle и связь с UI;
  не дублировать формирование протокольных запросов и разбор Twitch JSON.
- Один аккаунт бота и один личный канал пользователя. Пользователь исключил требование
  модератора: бот только отправляет сообщения. Владелец канала отдельно
  авторизует то же Twitch-приложение с `channel:bot`; модераторские разрешения
  не запрашиваются. Авторизацию бота и стримера показывать отдельными действиями
  с подтверждёнными аккаунтами, чтобы исключить вход не под тем пользователем.
  Канал API-режима брать из подтверждённой авторизации владельца, без ручного
  ввода и выбора чужого канала; настройки IRC сохраняются независимо.
- Авторизация бота с `user:write:chat` и `user:bot`, без разрешения чтения чата.
  Предлагаемый поток — Authorization Code с временным loopback callback,
  проверкой `state`, отменой и таймаутом. Redirect URL программа показывает
  для точного копирования в Twitch Console; публичный сайт не нужен.
- Получение App Access Token через Client Credentials; в отличие от
  пользовательского токена, по истечении он получается заново. Проверка
  пользовательской авторизации и обслуживание токенов выполняются программой.
- Отправка через Send Chat Message API с App Access Token; обработка
  `is_sent`, `drop_reason`, 401/403/429 и сетевых ошибок. Ответ API не считать
  доказательством прочтения сообщения зрителями.
- Сохранить маршрут редактора, исходный/обработанный текст, порядок очереди,
  её ограничение и защиту от повторов после неоднозначного результата.
  Адаптировать разбиение под лимит API 500 символов, не переносить IRC-байтовый
  бюджет на HTTP. Консервативный pacing оставить без оптимизации пропускной
  способности. Shared Chat ограничить исходным каналом явно.
- Общие настройки канала, автозапуска и тестовое сообщение остаются в панели.
  В API-режиме показывать подтверждённый аккаунт бота и готовность отправки
  вместо ожидания IRC JOIN. Одновременно активен только один транспорт;
  смена режима останавливает старые операции, устаревшие ответы игнорируются.

В панели и руководстве режим называется «Twitch API». Для текущего потока
используются отдельные аккаунты бота и владельца канала, без прав модератора.

## Вне объёма

Backend списка каналов и удалённые приглашения отложены до следующего этапа; UI второго этапа предусматривает расширение списка. Loopback URL работает только на компьютере,
где запущен TTSBard, и не предназначен для отправки другому человеку.
Собственный облачный сервис, общий аккаунт бота, EventSub, чтение чата,
раздел Chat Bots в списке участников, награды за баллы, модераторские команды,
объявления, ответы на сообщения и управление Shared Chat из UI. Не менять
TTS, OCR, другие интеграции и общую архитектуру приложения. Не создавать
универсальную платформу транспортов или отдельный мастер на новых экранах.

## Второй этап — панель и подготовка списка каналов

Согласован пользователем 2026-10-10. Реализация второго этапа выполнена; автоматические проверки пройдены. Базовая визуальная проверка IRC/API выполнена в Tauri, светлая тема/RU. Полная матрица тем, языков, увеличенного текста и реальной авторизации остаётся открытой; статус: in_progress.

- Смена режима останавливает подключение, сохраняет режим и не запускает его автоматически. Следующий запуск — вручную.
- Заголовок, статус, кнопки управления и две текущие галки остаются сверху вместе. После галок — разделитель и оформленная радиогруппа IRC/Twitch API.
- Форма меняется по режиму. После реквизитов — разделитель и общая по расположению кнопка «Сохранить» с действием для выбранного режима.
- Отдельное поле Redirect URL убрано; отдельный сброс удаляет авторизации с сохранением Client ID/Secret. Client ID скрыт по умолчанию с показом по запросу. Client Secret показывается статусом сохранения и заменяется через пустой ввод с отменой крестиком; просмотр доступен только для нового ввода. Бот и каналы используют Device Code Flow; адрес для регистрации приложения доступен в раскрываемой подсказке помощи.
- Под сохранением в API — две полноширинные панели друг под другом: аккаунт бота и каналы. Помощь соответствует выбранному режиму.
- Панель каналов проектируется под добавление нескольких авторизованных каналов и выбор ровно одного получателя. В этом проходе не вводить фиктивные каналы, неактивные кнопки приглашений или неподключённый selector: текущая авторизация остаётся рабочей.
- Backend списка, миграция единственного канала, действия забывания отдельных аккаунтов и удалённая авторизация — отдельные следующие задачи после согласования технического решения. Общий сброс не подменять отзывом разрешения Twitch.

## Авторизация каналов через Device Code Flow

2026-10-10 пользователь подтвердил успешную авторизацию канала через Device Code Flow. Переход каналов на этот поток утверждён пользователем и закреплён в [DECISION-026](../../decisions/026-twitch-device-flow.md). Это основной способ авторизации каналов: «Добавить канал» показывает ссылку с кодом и отдельные действия копирования и открытия; её можно отправить владельцу другого канала. TTSBard остаётся открытым до подтверждения или истечения ожидания. По следующему запросу пользователя бот также переведён на Device Code Flow с правами `user:write:chat`/`user:bot`; localhost callback в UI больше не используется. Автотесты и browser/mock-проверка пройдены; живой вход и отправка в Tauri требуют ручной приёмки.

## Несколько каналов

По запросу пользователя реализованы список разрешённых каналов, выбор одного получателя и удаление локально сохранённого доступа. Старый единственный канал переносится в список без повторного входа. Добавление сохраняет выбранного получателя; удаление выбранного канала оставляет список без выбора и останавливает API-подключение. Смена получателя при активном подключении автоматически перезапускает API-подключение на нового получателя. Сброс бота удаляет грант бота и останавливает подключение. Удаление доступа не отправляет отзыв токена в Twitch. Статус: in_progress — автоматические проверки и независимое ревью дополняются ручной приёмкой списка, переключения и удаления в приложении. Ранее подтверждённый пользователем эксперимент не считается проверкой новых сценариев списка.

## Исходные шаги и условия приёмки первого этапа

1. **Проверить осуществимость.** Локальный прототип с личным Confidential
   Client ID, отдельным ботом без прав модератора, разрешениями бота и
   `channel:bot` от владельца канала, а также App Access Token.
   Подтвердить отправку в Twitch и возможность повторной отправки после
   перезапуска. Уточнить соответствие локального хранения личного секрета
   требованиям Twitch: документация описывает Client Credentials как серверный
   поток; выбор Confidential сам по себе этого вопроса не решает. Если схема
   не подтверждается, остановить расширение, а не подменять токен пользовательским.
2. **Согласовать границы.** Уточнить два действия авторизации и
   способ хранения секретов (предложение: Windows Credential Manager либо DPAPI,
   без отдельного общего рефакторинга), callback и переходы статусов. В
   сохраняемых настройках и frontend-событиях не распространять токены;
   экспорт/логи не должны раскрывать секреты. Оформить decision при необходимости.
3. **Реализовать узкими задачами.** Сначала авторизация и хранение, затем
   API-отправка и переключение lifecycle, затем панель и документация.
   Детальная декомпозиция и задания DeepSeek через OpenCode остаются в
   `.work/ai/<work-id>/` по действующему workflow.
4. **Независимо проверить и принять.** Автоматические проверки дополняются
   ручной отправкой в Twitch и подтверждением результата пользователем.

## Критерии готовности

- Старые настройки запускают IRC без повторного ввода реквизитов; тестовая
  отправка и маршрутизация сохраняются в обоих режимах.
- API-настройка проходит от регистрации приложения до тестового сообщения
  без ручного переноса токенов, внешнего сайта и настройки роутера.
- Отмена/отказ OAuth, занятый callback-порт, неверный secret, другой аккаунт,
  совпадение бота с владельцем канала, отсутствие или отзыв `channel:bot`, отзыв доступа,
  истечение токена, лимит, обрыв сети и смена режима дают понятный результат.
- Нет двойной отправки, параллельных транспортов и автоматического повтора
  после неоднозначной отправки. Частичная отправка длинной фразы сохраняет
  корректную диагностику. Секреты и коды OAuth не попадают в логи.
- UI проверен в RU/EN, обеих темах, на минимальной ширине, с увеличенным текстом;
  состояния success/cancel/error/retry и устаревшие ответы покрыты. Эталон —
  существующие элементы TwitchPanel и действующие UI guidelines. Конкретный
  путь отчёта со скриншотами задаётся в implementation task; новые экраны не
  добавляются, описание панели в UI map обновляется при изменении состава.
- Rust-проверки только через `scripts/cargo.ps1`, полная сборка через
  `scripts/build.ps1`; целевые frontend-проверки, build и check-docs по задачам.
  Отчёт исполнителя не заменяет независимую проверку.
