# ROADMAP-132 — Пользовательская документация на английском и русском

## Цель и границы

Англоязычный пользователь может понять назначение TTSBard, скачать приложение,
выполнить первый запуск, настроить функции и интеграции, найти ответ на типовые
проблемы и прочитать обзор в PDF без знания русского языка. Русскоязычный
пользователь сразу видит свой язык на странице репозитория и сохраняет полный
доступ к инструкциям.

Это локализация пользовательских материалов, а не всей документации проекта.
Разработка, архитектура, решения, research, roadmap и implementation tasks
остаются на текущем языке. Перевод корневых `AGENTS.md` и `CLAUDE.md` на
английский — отдельно согласованное исключение, без расширения на инженерные
документы, на которые они ссылаются.

Направление согласовано пользователем 2026-10-19 и реализовано в тот же день.
2026-10-20 пользователь подтвердил просмотр PDF и структуры документации
и согласовал закрытие направления.

## Outcome

Один корневой README содержит EN/RU-блоки с двуязычной шапкой и переходами.
25 исходных пользовательских страниц перенесены в языковые каталоги;
вместе с новыми индексами проверяются 26 пар Markdown-страниц. Старые пути
в `docs/user/` и `docs/integrations/` сохраняют переходы и якоря;
исполняемый скрипт LunaTranslator не дублирован
и не изменён. Уточнены устаревшие описания LAN-доступа Input Server и
маршрутизации HTTP/OCR в WebView/Twitch по действующему коду.

`AGENTS.md` и `CLAUDE.md` переведены на английский с сохранением правил.
Инженерные материалы и `CHANGELOG.md` остаются русскими. Заявление разработчика
не изменялось: английский README содержит краткие сведения о поддержке и
явно помеченную ссылку на полный русский текст; перевод заявления не включён.

Постоянная сборка `scripts/build-overview.py` использует перенесённые тексты
и оформление существующего ReportLab-генератора, версию из `package.json`
и закреплённые зависимости. Оба PDF версии 1.6.0 содержат по две страницы.
По последующему указанию пользователя 2026-10-19 удалены старые корневые
FAQ, обзор Markdown и PDF; ссылки обновлены на языковые версии, генератор
больше не создаёт корневую PDF-копию. Сборка проверена из
другой рабочей директории в минимальной копии без `.work/`, включая имена
для вложений релиза. Все четыре страницы просмотрены после рендера;
версия, метаданные языка и ссылки проверены отдельно.

Проверка документации: 284 Markdown-файла и 26 языковых пар. Негативные
проверки: 6/6 для языковых пар, 18/18 для якорей и 6/6 для lifecycle задач.
Проверка пар и её тесты включены в существующий documentation CI. Новых
экранов и изменений runtime нет; реальные подключения к провайдерам и
интеграциям повторно не выполнялись. Это проверка документации и сборки PDF,
а не новый ручной прогон всего приложения.

Baseline и отчёт проверки находятся в локальной области
`.work/ai/2026-10-19-bilingual-user-docs/`.

Английские и русские пользовательские тексты дополнительно проверены
локальным LanguageTool 6.9-SNAPSHOT: 30 файлов / 1229 фрагментов на английском
и 29 файлов / 1300 фрагментов на русском. Подтверждённые замечания исправлены,
оставшиеся срабатывания рассмотрены вручную. Тексты не отправлялись в облако.
Это независимая инструментальная проверка грамматики; смысл перевода проверял
ведущий агент, отдельного независимого двуязычного рецензирования не было.
Локальные отчёты: `.work/ai/2026-10-19-translation-validation/report.md`
и `.work/ai/2026-10-20-russian-proofreading/report.md`.

## Согласованный объём

### Один корневой README с двумя языковыми блоками

- Сохранить один `README.md`: полный английский блок, горизонтальная черта,
  полный русский блок. Отдельный `README.ru.md` не нужен.
- До языковых блоков разместить название, короткое описание на обоих языках
  и заметные переходы `English | На русском` к разделам этой же страницы.
  Русский язык должен быть виден сразу, до прокрутки английского текста.
- В каждом блоке дать назначение, основные возможности, скачивание, быстрый
  старт, ограничения и ссылки на документацию/PDF соответствующего языка.
- Сохранить существенные сведения о проекте, поддержку, лицензию и авторство;
  не терять их при сокращении повторов. Большой исторический рассказ при
  необходимости вынести отдельно с понятной ссылкой и указанием языка.
- Использовать устойчивые якоря языковых блоков; проверить переходы и
  оглавление с повторяющимися заголовками.

### Пользовательские инструкции

Перевести и разместить симметрично в `docs/en/` и `docs/ru/`:

- все Markdown-инструкции из `docs/user/`, включая индекс и первый запуск;
- все Markdown-инструкции из `docs/integrations/`, включая индекс,
  `lunatranslator/README.md` и практические HTTP/SSE-контракты для подключения
  внешних клиентов;
- `docs/faq.md`;
- `docs/ttsbard-overview.md`;
- краткий обзор `docs/ttsbard-overview.pdf` на каждом языке.

Имена и вложенность парных файлов одинаковы; постфиксы `.en.md`/`.ru.md`
внутри языковых каталогов не используются. Пример целевых путей:

```text
README.md
docs/
  README.md
  en/
    README.md
    faq.md
    ttsbard-overview.md
    ttsbard-overview.pdf
    user/
      README.md
      guide.md
    integrations/
      README.md
      lunatranslator/
        README.md
  ru/
    README.md
    faq.md
    ttsbard-overview.md
    ttsbard-overview.pdf
    user/
      README.md
      guide.md
    integrations/
      README.md
      lunatranslator/
        README.md
```

Это пример структуры, а не сокращение списка переводимых инструкций.
`docs/README.md` получает двуязычный вход в пользовательские разделы;
инженерные разделы сохраняются с явным обозначением текущего языка.
Языковые индексы и инструкции позволяют перейти на соответствующую страницу
другого языка. Обычная навигация остаётся внутри выбранного языка.

### PDF и воспроизводимая сборка

Локальные источники сборки уже существуют: `.work/present/build.py` и
`.work/ai/2026-10-08-release-1.4/build-overview.py`. Оба используют ReportLab
и содержат собственный текст краткого обзора; это не конвертация подробного
Markdown один в один. Перед переносом сопоставить варианты с текущим PDF
и согласованными локальными материалами оформления.

- Использовать существующую сборку и оформление как основу; сохранить
  назначение краткого PDF отдельно от подробного обзора в Markdown.
- Перенести поддерживаемый генератор в `scripts/`, а необходимые шаблоны,
  стили и исходные тексты EN/RU — в постоянные файлы. Убрать зависимость
  от `.work/`, абсолютных путей конкретного компьютера и старых релизных копий.
- Один запуск должен собирать оба языка. Описать команду, зависимости и
  требования к шрифтам с кириллицей; зафиксировать поддерживаемое окружение.
  Инструкцию сборки разместить в существующей документации разработки,
  без перевода всего инженерного раздела.
- Версию брать из источника версии проекта. Названия, метаданные и ссылки
  внутри PDF соответствуют языку; ссылки работают вне локального checkout.
- Текущие PDF хранить в языковых каталогах. Для вложений релиза использовать
  различимые имена вида `TTSBard-overview-<version>-en.pdf` и `...-ru.pdf`.
  Перевыпуск исторических PDF не требуется.
- Визуально проверить обе сборки: кириллицу, переносы, поля, разрывы страниц,
  ссылки и отсутствие обрезанного текста. Не считать успешный запуск
  генератора подтверждением качества вёрстки.

### Инструкции агентов

Перевести `AGENTS.md` и `CLAUDE.md` на английский, сохранив различия ролей,
действующие правила, ограничения и смысл ссылок. Не менять workflow,
правила согласования, Windows build wrappers или политику делегирования
под видом перевода. Целевые документы ссылок могут оставаться русскими.

## Термины и достоверность

Локализация интерфейса уже реализована. Источник названий меню, кнопок,
настроек и уведомлений — соответствующие ключи в `locales/en.json` и
`locales/ru.json`; native-строки дополнительно сверять с
`src-tauri/locales/en.json` и текущим кодом. Существующие английские названия
UI использовать дословно, а не переводить заново независимо от приложения.

Не переводить API endpoints, JSON-ключи, команды, имена моделей и файлов
как обычный текст. Примеры сохраняют работоспособность. Возможности,
ограниченные русским языком, например русская орфография и RUAccent,
описываются с этим ограничением и в английских материалах.

Скриншоты с текстом интерфейса подготовить на соответствующем языке, если
они присутствуют в инструкциях. Общие схемы и изображения без языкового
текста можно переиспользовать.

## Необходимые сопутствующие изменения

- Обновить внутренние ссылки и якоря во всём репозитории после переноса.
  Исправление пути в инженерном документе не означает его перевод.
- На прежних Markdown-путях внутри `docs/user/` и `docs/integrations/`
  оставить короткие страницы с EN/RU-переходами вместо второй полной копии.
  По уточнению пользователя корневые FAQ, обзор Markdown и PDF не сохраняются;
  внутренние ссылки должны вести непосредственно в языковые каталоги.
- Не дублировать исполняемый `selfbuild_tts.py` LunaTranslator по языковым
  каталогам: сохранить один канонический файл, обновить ссылки и команды
  установки в обоих переводах, сохранить существующий путь скачивания.
- Обновить `scripts/check-docs.ps1`: допустимую структуру, проверку языковых
  пар, ссылок и якорей. Не ослаблять существующие lifecycle-проверки.
- Зафиксировать правило сопровождения: пользовательское изменение отражается
  в обоих языках и затронутых PDF; при задержке перевода явно указывается
  актуальность. Русский материал — исходник первого перевода, но названия
  английского UI берутся из каталога приложения.

Дополнительно оценить `DEVELOPER_STATEMENT.md`, на который ссылается README:
границы поддержки важны обычному пользователю. Рекомендуется включить
английскую версию с сохранением даты и смысла исходного заявления; это
предложение к объёму, не молчаливое утверждение нового содержания.
Аналогично проверить пользовательские ссылки на сторонние notices и файлы
скачивания: обязательный шаг не должен неожиданно требовать русского текста.
Официальный `LICENSE` и сторонние юридические тексты не переводить и не
подменять неофициальным переводом в рамках этого направления.

## Вне объёма

`CHANGELOG.md` остаётся только на русском, включая новые записи. Английская
версия истории изменений сейчас не нужна; при появлении потребности её объём
и формат рассматриваются отдельно.

Перевод инженерной документации, research, roadmap, задач и всей истории
changelog; изменение локализации или поведения приложения; новый сайт
документации, GitHub Pages, SEO и публикация; сервис управления переводами;
третьи языки; новая система PDF-вёрстки вместо существующей без необходимости.
