# Согласованное управление жизненным циклом интеграций

## Outcome

Направление закрыто по явному одобрению пользователя 2026-10-06.
Реализовано согласованное управление запуском, остановкой и перезапуском
WebView, Twitch, VTube Studio и входящего сервера: управление и параметры
подключения блокируются на время операции, сохранение черновика не создаёт
дополнительного перезапуска, результат подтверждается runtime-состоянием.
WebView получил отдельную команду перезапуска; входящий сервер использует
существующую команду запуска для одного rebind-цикла.

Автоматические проверки реализации перечислены ниже. При закрытии новые
проверки не запускались; подробный результат ручных сценариев не зафиксирован.
Разделы исходного состояния и плана ниже сохранены как исторический контекст.

## Цель

Унифицировать пользовательское поведение запуска, остановки, перезапуска и
применения настроек WebView, Twitch, VTube Studio и входящего сервера.
Оформление завершено в [ROADMAP-121](../completed/121-ui-visual-consistency.md);
приёмка жизненного цикла остаётся самостоятельной задачей.

## Фактическое состояние (проверено по коду 2026-10-05)

Большая часть исходных наблюдений уже закрыта сохранением черновика перед
запуском и слотами операций, разрешаемых runtime-событиями (коммит
`0b0b9c1` и последующие):

- WebView: `startPending` блокирует запуск; слот `pendingStart` закрывается
  только статусами running/error, промежуточный stopped его не отменяет;
  FIFO-drain записей; ошибка сохранения запрещает запуск; сообщения
  различают сохранение и запуск (`webview.launch.*`).
- Twitch: `connectPending` блокирует старт/перезапуск; слот `pendingConnect`
  разрешается статусами Connected/Error; сохранение с изменёнными реквизитами
  работающего клиента само инициирует reconnect, второй `restart_twitch`
  из одной операции не создаётся; backend — одиночное событие Restart.
- VTube Studio: connect/restart — синхронный invoke с подтверждённым
  результатом; `busy` блокирует кнопки и поля; промежуточные события во
  время операции игнорируются (`connectionOperationPending`).
- Входящий сервер: `startPending`/`stopPending` блокируют кнопки; слот
  `pendingStart` разрешается событием статуса; supervisor коалесцит wake,
  подавляет дубликаты статусов, port-change перебиндывает listener.

Оставшиеся пробелы (подтверждены по исходникам):

- WebView — ядро задачи. `restartServer()` делает две записи `enabled`
  (false, затем true), каждая отправляет `RestartWebViewServer`: два полных
  цикла stop/start, между ними видимый stopped. В этом окне панель по
  runtime-статусу переключается на ветку запуска: кнопка старта кратко
  доступна, а поля адреса/порта и «Сохранить» разблокируются. Отдельной
  backend-команды перезапуска нет. Кнопка перезапуска не показывает
  состояние операции; стоп доступен во время starting/restart.
- Twitch: стоп не блокируется на время `connectPending`; поля реквизитов
  не блокируются на время операции. Короткое окно между ответом команды и
  событием Connecting оставляет старт доступным при Disconnected.
- VTube Studio: host/port не блокируются на время операции — «Сохранить»
  блокируется `busy`, а поля ввода остаются доступными. Статус «Подключение…»
  при перезапуске корректен: VTube Studio — клиент, а не сервер; остальное
  соответствует цели.
- Входящий сервер: нет действия перезапуска (кнопки и команды); явный
  restart командой `set_run_request(true) + wake` даёт один чистый rebind.

## Целевое поведение

- Отключено: запуск доступен, стоп недоступен; работает: перезапуск и стоп доступны.
- На время запуска, перезапуска и остановки управление блокируется до фактического
  завершения или ошибки. Поля параметров подключения блокируются на время операции.
- Нажатая кнопка сохраняет свою роль и показывает индикатор операции;
  промежуточный stopped не открывает запуск. Индикатор «Перезапуск…» — для
  серверных панелей (WebView, входящий сервер); клиентские Twitch и VTube
  Studio при любой операции показывают «Подключение…».
- Стоп во время запуска/перезапуска недоступен; отмена операции не входит в scope.
- Запуск/перезапуск фиксирует текущий черновик подключения, сохраняет и применяет
  его ровно один раз. Ошибка сохранения запрещает последующий запуск.
- Если сохранение прошло, а подключение не удалось, значения остаются сохранёнными,
  сообщение различает результат сохранения и результат подключения.
- Применение изменённого адреса/порта не создаёт дополнительный restart поверх
  уже начатой операции. Независимые настройки не запускают переподключение случайно.
- Отдельное «Сохранить» при работающем подключении с изменёнными параметрами
  выполняет один перезапуск (семантика текущих `saved_restarting` /
  `saved_reconnecting`); без изменений подключения — только запись.
- Восстановление после потерянного подтверждения — runtime-снимок статуса при
  (повторном) входе на панель; вечной блокировки нет, статус `restarting`
  не вводится.

## Короткий план

1. WebView backend: команда `restart_webview_server` — один цикл перезапуска
   без переключения `enabled` и без записи настроек.
2. WebView фронт: `restartServer` = одна запись draft (enabled не трогается);
   если ответ `saved_restarting`, restart уже начат сохранением — команду не
   звать (паттерн Twitch); иначе одна команда. Ввести `restartPending`:
   кнопки и поля держат роли всю операцию, «Перезапуск…» в статусе, стоп
   недоступен во время запуска/перезапуска.
3. Twitch фронт: блокировать стоп и поля реквизитов на время
   `connectPending`/Connecting (семантика backend не меняется).
4. VTube Studio: блокировать host/port на время `busy`; статус «Подключение…»
   при перезапуске сохранить (клиент), остальное не трогать.
5. Входящий сервер: backend-команда перезапуска (`set_run_request(true)` +
   `wake`), кнопка и `restartPending` в панели по образцу WebView.
6. Тесты: порядок событий WebView (включая сегодняшний двойной цикл —
   воспроизвести и зафиксировать одиночный), блокировки кнопок/полей на время
   операций, поздние/повторные события, повторный вход на панель.

Общие цвета и геометрия кнопок остаются в существующем CSS; единый сложный
контроллер интеграций не вводится. Реализацию выполняет Codex напрямую,
без task-флоу OpenCode; отдельный коммит по одобрению пользователя.

## Реализация (2026-10-05)

Выполнено по плану, пункты 1–6; отличия от плана:

- Входящий сервер: отдельная backend-команда перезапуска не потребовалась —
  `start_input_server` на работающем сервере (run_request уже установлен +
  один wake) даёт ровно один rebind-цикл supervisor'а. Вместо этого контракт
  `save_input_server_settings` теперь возвращает `saved`/`saved_restarting`,
  чтобы перезапуск поверх сохранения с изменившимся портом не создавал
  второй цикл.
- WebView: слот операции `pendingStart` стал реактивным и держит блокировки
  кнопок и полей до runtime-подтверждения (не только фазу команды); добавлен
  `stopPending` для полной блокировки управления на время стопа.

Проверки: vitest 1374 (включая новые restart-сценарии WebView, входящего
сервера и guard стопа Twitch), vue-tsc, cargo check/clippy (предexisting
warning в `storage.rs` не относится к задаче), cargo test --lib 2210,
check:ipc, check:locales, check:settings — все зелёные. Направление закрыто пользователем 2026-10-06; подробный отчёт ручной приёмки не зафиксирован.

## Сценарии проверки

Проверить в Tauri все четыре панели: обычный запуск/стоп/перезапуск, быстрые
повторные клики, промежуточные и поздние статусы, ошибки сохранения и
подключения, изменённый порт/адрес, уход с панели во время операции, повторный
вход. Тесты должны воспроизводить порядок событий, обнаруженный в runtime,
включая лишний цикл WebView; проверки только stopped → running недостаточно.
