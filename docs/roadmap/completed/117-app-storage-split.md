# ROADMAP-117 — Разделение данных приложения: Roaming, Local и %TEMP%

## Контекст

До начала реализации все данные приложения писались в единый корень
`%APPDATA%\ttsbard` (Roaming-профиль).
Более десятка мест строят этот путь независимо: `dirs::config_dir().join("ttsbard")`
(`src-tauri/src/history.rs`, `src-tauri/src/config/settings.rs`,
`src-tauri/src/ocr/service.rs`, `src-tauri/src/state.rs`, `src-tauri/src/tabs.rs`,
`src-tauri/src/webview/server.rs`, `src-tauri/src/commands/mod.rs`) плюс прямое
чтение `APPDATA` в `src-tauri/src/telegram/bot.rs` и `src-tauri/src/lib.rs` (логи).

Фактические объёмы на рабочей машине: `models` ~940 МБ, `logs` ~107 МБ,
`audio_cache` ~82 МБ, `temp` ~3 МБ. Roaming-расположение нарушает Windows-семантику
Known Folders: в доменных средах эти данные синхронизируются с сервером профиля.

Исходные проблемы и ограничения:

- временные файлы Telegram (`get_temp_dir` в `telegram/bot.rs`) пишутся в
  `%APPDATA%\ttsbard\temp`; итоговые файлы `silero_tts_<msg_id>.mp3` никогда не
  удаляются — чистятся только `.part` при сбое скачивания;
- `audio_cache` растёт без лимита и эвикции; при этом ключ детерминирован
  (hash текста, провайдера, голоса и эффектов), а файлы регенерируемы повторным
  синтезом;
- модели (`models/piper`, `models/ocr`, `models/ruaccent`, accentors) ищутся
  только в config dir; приложение их не скачивает и не распаковывает (ручное
  размещение), у пользователей фактически не используются — миграция не нужна;
- в `%LOCALAPPDATA%` уже есть следы приложения: ONNX Runtime ведёт собственный
  кеш в `TTSBard\ort-cache` (создаётся библиотекой, а не кодом приложения; на
  NTFS это та же папка, что и `ttsbard`), Tauri использует отдельный
  `com.al.ttsbard` для WebView-данных.

`espeak-ng-data` установщик кладёт рядом с exe (Tauri resource, 19 МБ,
`tauri.conf.json` → `espeak-ng-data`), поэтому установленная и portable-копии
используют один механизм. Текущая цепочка поиска eSpeak: resource_dir →
эффективный корень «Данные программы» → cwd → папка exe
(`tts/piper/runtime.rs::init_espeak_data`, ROADMAP-119). Это отдельный поиск
ресурсов runtime; изменение корней пользовательских моделей его не меняет.

## Цель

Данные разделены по семантике ОС, путь каждого вида определяется в одном месте:

- настройки, история и пользовательские шаблоны остаются в Roaming (`%APPDATA%\ttsbard`);
- регенерируемый аудио-кеш и основной каталог моделей живут в «Данных программы»
  (`storage.data_dir`, по умолчанию `%LOCALAPPDATA%\ttsbard`); дополнительные
  модели обнаруживаются в рабочей директории процесса с более высоким приоритетом;
- транзиентные файлы Telegram живут в `%TEMP%\ttsbard` секунды и удаляются
  детерминированно после потребления;
- пользователь может задать путь аудио-кеша в настройках, с переносом существующих
  файлов и fallback на дефолт при недоступности.

## Этапы

### Подтверждённый результат на 2026-10-01

Одноразовая миграция аудио-кеша реализована: backend-only поле
`storage.legacy_audio_cache_migrated` сохраняется в `settings.json` атомарно
после полного переноса либо подтверждения отсутствия старого каталога. При
`true` миграция полностью пропускается, даже если legacy-каталог появился снова.
Неполный перенос и ошибка сохранения маркера допускают повторную попытку при
следующем старте. Изменение остальных настроек сохраняет маркер.

Перенос выполняется синхронно до создания приложения и UI, после проверки
single-instance и настройки логирования. Используется rename, при невозможности
— copy + удаление источника (в том числе между дисками). Переносятся только
WAV-файлы верхнего уровня; неожиданные файлы и вложенные каталоги сохраняются
и не позволяют считать миграцию завершённой. Фонового переноса нет.

SoundPanel-звуки, привязки и пользовательские HTML/CSS-шаблоны WebView остаются
в Roaming. Внутренние данные движка WebView относятся к отдельному Local-каталогу.
Telegram-аудио читается в память и удаляется из temp до декодирования, записи
обработанного WAV в кеш и воспроизведения.

Изменение маркера независимо проверено через `scripts/cargo.ps1`: 18 целевых
тестов миграции, 12 тестов хранения и `check` прошли. Эти проверки относятся
к этапу реализации; пользовательская приёмка зафиксирована в Outcome ниже.

### 1. Центральный модуль путей и temp в %TEMP%

Ввести один модуль разрешения путей (config root, local root, temp root, корни
моделей), перевести на него существующие конструкции `dirs::config_dir()`.
Временные файлы Telegram переместить в `%TEMP%\ttsbard`, удалить файл сразу после
чтения в память (включая error-ветки после успешной загрузки, например
unsupported OGG codec), зачистить содержимое `%TEMP%\ttsbard` при старте
(безопасно благодаря single-instance). Одноразово удалить legacy-папку
`%APPDATA%\ttsbard\temp` по точному пути, best-effort.

### 2. Аудио-кеш в %LOCALAPPDATA%

Дефолт кеша — `%LOCALAPPDATA%\ttsbard\audio_cache`. Одноразовая миграция при
старте с persistent-маркером `storage.legacy_audio_cache_migrated` в том же
`settings.json` (отсутствующее поле трактуется как `false`). Если маркер уже
`true`, legacy-каталог больше не проверять. Иначе, если существует
`%APPDATA%\ttsbard\audio_cache`, переносить `*.wav`
по одному `fs::rename` с fallback copy + удаление источника (занятые пропускать),
пустую старую папку удалить, ретрай
на следующем старте, пока миграция не завершена. Маркер ставить только после
полного переноса и удаления пустой старой папки либо подтверждения, что старой
папки нет; сохранять через штатный механизм settings без потери других полей.
При ошибке переноса или сохранения маркера оставить возможность повторной
попытки. Маркер относится только к legacy-миграции и не блокирует перенос при
смене пути кеша пользователем. CacheMiss остаётся естественным fallback: пропавший файл
замещается повторным синтезом, fallback-чтение из старой папки не вводится.
Формат `phrase_history.json` не меняется — записи ссылаются на `cache_key`, а не
на путь.

### 3. Модели в рабочей директории и «Данных программы»

Утверждённая 2026-10-03 цепочка для Piper, OCR и RUAccent: рабочая директория
процесса (`cwd`), затем эффективный корень «Данные программы» (`storage.data_dir`
либо `%LOCALAPPDATA%\ttsbard`). В каждом корне используются существующие
подкаталоги `models/piper`, `models/ocr`, `models/ruaccent`. Каталоги объединяются
по валидным дескрипторам; при совпадении ID побеждает модель из cwd. Повреждённая
модель в первом корне не скрывает валидную модель во втором.

`cwd` не равнозначна папке exe: её задаёт способ запуска, в том числе поле
«Рабочая папка» ярлыка. Приложение не меняет cwd. Отдельного поиска рядом с exe
или в `resource_dir` для пользовательских моделей нет; одинаковые корни не
сканируются повторно. При недоступности cwd остаётся поиск в «Данных программы».
Сканирование cwd не создаёт каталогов и не меняет файлы. Создание каталогов и
перенос управляемых данных относятся только к «Данным программы»; модели cwd
не включаются в перенос. Legacy-чтение моделей из `%APPDATA%\ttsbard` не вводится.
Уточнение от 2026-10-05: при запуске до обнаружения моделей выполняется
одноразовый перенос `%APPDATA%\ttsbard\models` в `models` эффективной папки
«Данные программы». Независимый backend-only маркер
`storage.legacy_models_migrated` сохраняется после полного переноса и удаления
старого каталога либо подтверждения его отсутствия. Отсутствующее поле означает
`false`; ошибка переноса или сохранения маркера допускает повтор на следующем
старте и не блокирует запуск. Существующие файлы не перезаписываются: идентичные
копии допускают повтор, различающиеся файлы отклоняют перенос до копирования.

Реализация использует общие корни поиска cwd → «Данные программы» для Piper,
OCR и RUAccent. Стартовое обнаружение, обновление списков и загрузка моделей
согласованы с этой цепочкой; выбранный `storage.data_dir` заменяет стандартный
Local-корень.

### 4. UI: папки и перенос данных

Единый блок «Папки» в General-настройках содержит «Конфигурация»
(`%APPDATA%\ttsbard`, открытие) и «Данные программы»
(`%LOCALAPPDATA%\ttsbard` по умолчанию, открытие, изменение и сброс иконкой).
Общий корень данных задаётся `storage.data_dir`; внутри находятся `audio_cache`
и `models`. Legacy `storage.audio_cache_dir` сохраняет прежнюю семантику до
успешного переноса, после которого override очищается.

Смена и сброс пути открывают подтверждение с путями и объёмом данных, затем
блокирующее модальное окно с подготовкой, прогрессом по байтам и завершением.
Перенос проверяет `models` и `audio_cache` отдельно. Если одна и та же категория
содержит файлы в источнике и назначении, весь перенос отклоняется до копирования:
интерфейс сообщает о необходимости ручного переноса и повторной попытки.
Автоматического объединения и перезаписи нет. Пустой источник допускает
заполненное назначение и смену корня без изменения существующих файлов;
пустые подпапки без файлов не считаются данными. При пустом назначении
перенос копирует управляемые каталоги,
сохраняет настройку после полного копирования и затем удаляет неизменившиеся
исходники. Ошибка оставляет прежний путь и исходные данные, удаляет созданные
операцией файлы назначения и позволяет повторить попытку. Фоновые операции
кеша синхронизированы с переносом. Вложенные пути, конфигурационный корень и
symlink/junction-пути отклоняются. После смены корня нужен перезапуск для
сервисов моделей, запоминающих путь при запуске. При недоступности пути при
старте используется стандартный корень с предупреждением в логах.

## Порядок реализации

Этапы выполняются отдельными task и независимо проверяются, строго по порядку:
этап 1 открывает остальным центральный модуль путей; этапы 2–3 зависят от него,
этап 4 зависит от 2. Между этапами 2 и 3 нет зависимости.

## Критерии результата

- После сессии синтеза через Telegram в `%TEMP%\ttsbard` нет файлов; legacy
  `%APPDATA%\ttsbard\temp` удалена и не создаётся вновь.
- `audio_cache` читается и пишется в `%LOCALAPPDATA%\ttsbard\audio_cache`;
  после первой миграции в `%APPDATA%\ttsbard` папки `audio_cache` нет, история
  фраз воспроизводится без повторного синтеза.
- После завершённой миграции маркер сохранён и последующие запуски не проверяют
  legacy-каталог; неполная миграция не ставит маркер и допускает повторную попытку.
- Piper, OCR и RUAccent обнаруживаются в cwd → «Данные программы» при старте,
  обновлении и загрузке. Валидные модели с разными ID из обоих корней доступны;
  одинаковый ID выбирается из cwd, невалидный кандидат допускает fallback.
- При заданном `storage.data_dir` второй корень — выбранная папка, без отдельного
  fallback-чтения моделей из Local. Сканирование cwd не создаёт каталогов.
- Запуск с cwd, отличной от папки exe, использует cwd; поиск только рядом с exe
  и отдельный resource-корень пользовательских моделей исключены. Смена «Данных
  программы» требует перезапуска сервисов моделей, как и ранее.
- Смена пути кеша в UI переносит файлы и сохраняет настройку; недоступный путь
  при старте не блокирует запуск — используется дефолт и warning.
- Проходят целевые Rust-тесты через `scripts/cargo.ps1`, `npm test` и
  `npm run build` для затронутого frontend.

## Не входит

- Логи: ротация и перенос из Roaming — отдельное направление.
- LRU-эвикция и лимит размера кеша, отображение размера и кнопка очистки —
  осознанно исключены; возвращаются вместе с функцией, которой служат.
- Скачивание и установка моделей приложением, очистка orphan-каталогов
  (`models/pocket`, остаточные zip-архивы) на пользовательских машинах.
- Изменение расположения `espeak-ng-data` — установщик уже кладёт его рядом с
  exe, установленная и portable-копии используют один и тот же механизм.
- Перенос soundpanel-звуков и webview-шаблонов — пользовательские и конфигурационные
  данные Roaming-семантики.

## Outcome

Данные разделены между конфигурационным Roaming-корнем, управляемым корнем
«Данные программы» и `%TEMP%`. Реализованы однократная стартовая миграция
legacy-аудио-кеша с сохраняемым маркером, общие корни поиска пользовательских
моделей и смена папки данных через UI с переносом управляемых файлов.

2026-10-04 пользователь подтвердил готовность ROADMAP-117, отдельно подтвердив
однократную миграцию при запуске и работающую смену папки. Roadmap закрыт
по этой приёмке. При оформлении закрытия дополнительные runtime-проверки
не выполнялись; новые результаты проверки ошибок переноса не заявляются.
