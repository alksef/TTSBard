# ROADMAP-131 — Режим отправки через Twitch API

## Цель

Добавить в существующую панель Twitch отправку реплик через Helix API от
отдельного аккаунта бота без прав модератора, сохранив классический IRC.

## Outcome

Закрыто по указанию пользователя 2026-10-10, входит в версию 1.5.0.
Первоначальный объём с одним каналом и localhost callback расширен:
реализованы Device Code Flow для бота и владельцев каналов, список каналов
и выбор одного получателя. Старый loopback-код и его специализированные
тесты удалены. Направление перенумеровано из ROADMAP-132 в ROADMAP-131
после переноса SQLite-драфта из публичной дорожной карты в локальную рабочую область.

### OAuth и обслуживание токенов

- Личное Confidential-приложение пользователя с Client ID/Client Secret;
  общий секрет в сборку не включается. Протокол реализован через
  `twitch_api` и `twitch_oauth2` (twitch-rs).
- Бот авторизуется с `user:write:chat` и `user:bot`, владелец каждого канала —
  с `channel:bot`. Аккаунты бота и владельца канала должны различаться.
- Оба входа используют Device Code Flow: ссылка активации с кодом открывается
  или копируется явным действием. Её можно передать владельцу канала или
  открыть на другом устройстве; TTSBard остаётся открытым до завершения.
  Локальный callback и отдельное поле Redirect URL в панели не используются.
- Ожидание ограничено 300 секундами и сроком кода Twitch; polling учитывает
  интервал сервера и `slow_down`. Предусмотрены отмена, отказ и истечение срока.
- `TwitchAuthCoordinator` проверяет аккаунты, Client ID и разрешения,
  валидирует авторизации при простое и обновляет пользовательские токены.
  Ротация refresh-токена сохраняется; временная ошибка проверки не удаляет грант.
  App Access Token получается через Client Credentials и обновляется отдельно.
- Поколение состояния и идентификатор сессии защищают от запоздалого результата
  после отмены, изменения реквизитов, сброса или смены получателя.

### Хранение и каналы

- Реквизиты и токены Twitch API хранятся в разделе `twitch` общего
  `%APPDATA%\ttsbard\secrets.dat`, зашифрованного Windows DPAPI текущего
  пользователя. Запись атомарная; секреты не передаются в frontend DTO и логи.
  Другие интеграции этим изменением в хранилище не переводятся.
- Сохранённый единственный канал прежней схемы раздела переносится в список.
  Отдельный экспериментальный файл `twitch-api.credentials` не импортируется:
  для него нужен повторный вход. DPAPI-файл не является переносимым экспортом.
- Первый добавленный канал выбирается автоматически. Последующее добавление
  сохраняет выбор; отправка всегда идёт только в один выбранный канал.
- Смена получателя при активном API-подключении перезапускает его на новый канал.
  Удаление выбранного канала сбрасывает выбор и останавливает подключение.
- Удаление доступа забывает канал только локально, без Twitch revoke.
  Сброс бота удаляет его грант и останавливает подключение; общий сброс
  авторизаций сохраняет Client ID/Secret. Отзыв разрешения на стороне Twitch
  выполняется пользователем в настройках подключений Twitch.

### Доставка и панель

- IRC остаётся режимом по умолчанию для старых настроек. Одновременно работает
  один транспорт; смена IRC/API останавливает подключение до ручного запуска.
  Маршруты редактора, очередь, автозапуск и тестовое сообщение сохранены.
- Helix Send Chat Message использует App Access Token; длинные фразы делятся
  по 500 Unicode-символов. `for_source_only=true` ограничивает Shared Chat
  исходным каналом. Обрабатываются `is_sent`, `drop_reason`, 401/403/429,
  сетевые ошибки и частичная отправка без автоматического дублирования хвоста.
- Общие управление и галки расположены сверху, ниже — режим, реквизиты
  и сохранение; в API затем идут панели бота и каналов. Client ID скрыт
  до запроса просмотра; Client Secret показан статусом, заменяется новым
  вводом с возможностью отмены, просмотр доступен только для нового ввода.
- IPC покрывает статус, сохранение клиента, начало/завершение/отмену входа,
  сброс авторизаций, выбор и локальное удаление канала. Frontend использует
  `useTwitchApiAuth`; локализации и контракты предусмотрены для RU/EN.

## Проверка и ограничения при закрытии

Документ сверен с текущими `twitch/auth.rs`, `device_oauth.rs`, `oauth.rs`,
`credentials.rs`, `api.rs`, IPC-командами и `useTwitchApiAuth.ts`.
В коде есть тесты отмены и конкурирующих сессий, refresh/validate,
миграции каналов, выбора получателя и ошибок доставки.

Ранее зафиксированы успешная авторизация канала пользователем, автоматические
проверки, browser/mock-проверка и базовая визуальная проверка Tauri в RU/светлой
теме. Закрытие по указанию пользователя не означает новый полный ручной прогон:
в этой сессии реальные OAuth/отправка, все сценарии каналов и полная матрица
тем, языков и увеличенного текста повторно не проверялись. Проверка документации
не заменяет проверку runtime и актуальных требований Twitch.

## Вне объёма

Облачный посредник, общий бот приложения, EventSub, чтение чата, модераторские
команды, награды, объявления, ответы на сообщения, управление Shared Chat
из UI и автоматический отзыв разрешений Twitch. Новые экраны и универсальная
платформа транспортов не вводились.
