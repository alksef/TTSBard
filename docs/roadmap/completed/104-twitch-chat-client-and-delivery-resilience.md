# ROADMAP-104 — Надёжный Twitch-клиент и доставка сообщений

## Контекст

Текущая интеграция самостоятельно реализует Twitch IRC поверх TCP/TLS:
авторизацию, JOIN, PING/PONG, обработку `RECONNECT`, статус соединения и
переподключение с backoff. После ROADMAP-095 транспортные обрывы восстанавливаются
лучше, однако корректность по-прежнему зависит от нескольких связанных фоновых
задач и собственного разбора IRC.

Наблюдаемый пользовательский дефект — Twitch иногда перестаёт отправлять
сообщения и восстанавливается только после перезапуска приложения. Текущий
клиент считает startup успешным сразу после записи PASS/NICK/JOIN, вручную
синхронизирует listener и writer и запускает Twitch supervisor только один раз.
Ошибки внутри этой цепочки способны оставить runtime без работающего владельца
соединения.

Официальная документация Twitch требует отвечать на PING, переподключаться и
повторно входить в каналы после `RECONNECT`. Twitch рекомендует EventSub и Send
Chat Message API для новых полнофункциональных чат-ботов, но для текущего
локального сценария одной исходящей IRC-интеграции переход на Helix потребовал бы
нового Client ID, OAuth scopes и получения user IDs. Поэтому ближайший шаг — не
смена Twitch API, а замена самописного IRC lifecycle на профильную Rust-библиотеку
`twitch-irc`.

## Цель

Устранить зависимость надёжности Twitch от собственного socket lifecycle и
закрыть Twitch-specific пробелы, которые не решаются самой заменой библиотеки.
Публичные настройки, Tauri-команды, маршрутизация фраз и UI-статусы должны
сохранить совместимое поведение.

## Границы решения

Направление состоит из двух последовательных Twitch-блоков. Первый заменяет
транспорт и протокольный lifecycle. Второй закрывает свойства Twitch runtime и
доставки, которыми библиотека не может владеть за приложение. Ограничения длины
текста и разбиение фраз вынесены в ROADMAP-106.

## P1 — Переход на `twitch-irc`

### Результат

Самописные TCP/TLS reader/writer, PING/PONG и reconnect loop заменены
`twitch-irc`. Приложение сохраняет собственный owner для runtime-настроек,
пользовательских команд и отображаемого статуса, но не дублирует протокольную
машину состояний библиотеки.

### Scope

- Подключить закреплённую совместимую версию `twitch-irc` с минимальным набором
  transport features и проверить её лицензию/notice по принятому процессу.
- Создавать клиент со статическими credentials из текущих username/token и
  входить ровно в один настроенный канал.
- Использовать безопасный метод `say`, чтобы пользовательский текст не
  интерпретировался как IRC-команда.
- Преобразовывать события библиотеки в существующий UI-контракт
  `Disconnected`, `Connecting`, `Connected`, `Error` без изменения frontend API.
- Считать соединение `Connected` только после подтверждённого входа в целевой
  канал, а не после создания TCP/TLS-соединения или постановки JOIN в очередь.
- Сохранить различие между terminal authentication/configuration error и
  временным transport failure. Временный обрыв должен восстанавливаться с
  повторным JOIN средствами библиотеки.
- Сохранить семантику ручных Connect, Disconnect, Restart, изменения настроек,
  запуска при старте и общего shutdown token.
- Обеспечить детерминированное завершение клиента: при Stop/Restart не должны
  оставаться клоны handle, удерживающие старый background runtime.
- Сохранить текущие маршруты доставки: обычная фраза через speech pipeline и
  Twitch-only команда продолжают использовать одного owner клиента.
- Удалить ставшие ненужными TLS/reconnect реализации и прямые зависимости
  только после проверки, что они не используются другими подсистемами.

### Не входит в ROADMAP-104

- ограничение, обрезка или разбиение пользовательского текста;
- общий provider-aware контракт длины фразы;
- Silero/Telegram и другие TTS-провайдеры;
- повтор пользовательского сообщения после неоднозначного сетевого сбоя;
- доказательство появления сообщения в чате;
- миграция на EventSub или Send Chat Message API;
- изменения панели настроек и persisted schema без отдельной необходимости.

### Проверки P1

- Успешное подключение и подтверждённый JOIN дают `Connected`.
- Неверный token даёт устойчивый `Error` и не запускает бесконечный reconnect.
- Закрытие сокета, серверный `RECONNECT` и временная недоступность сети приводят
  к повторному подключению и JOIN без перезапуска приложения.
- Stop и shutdown завершают фоновые задачи; позднее событие старого клиента не
  возвращает статус Connected.
- Restart и изменение credentials/channel не устанавливают stale client.
- Отправка до подтверждённого JOIN возвращает typed unavailable error.
- Повторные Connect/Disconnect/Restart не создают параллельных клиентов.
- Целевые Rust-тесты и `check` запускаются через `scripts/cargo.ps1`; полный
  debug build — через `scripts/build.ps1`.

## P2 — Twitch runtime и доставка вне ответственности библиотеки

### Почему смены библиотеки недостаточно

`twitch-irc` владеет соединением и повторным JOIN, но приложение по-прежнему
владеет очередью, частотой отправки, статусами UI и семантикой результата.
Twitch может молча отбросить IRC-сообщение из-за rate limit или правил канала;
успешный вызов библиотеки означает локальную отправку, а не подтверждённое
отображение в чате.

### Scope

- Добавить ограниченную исходящую очередь и rate limiter. Для обычного аккаунта
  учитывать 20 сообщений за 30 секунд и не более одного сообщения в секунду на
  канал, если аккаунт не broadcaster/moderator/VIP; не предполагать повышенные
  лимиты без подтверждённого статуса.
- Определить bounded capacity и backpressure: переполнение не должно потреблять
  неограниченную память или молча терять сообщение.
- Не повторять автоматически сообщение после неоднозначной ошибки записи, если
  оно могло уже попасть в Twitch, чтобы не создавать дубликаты.
- Различать `queued`, локально `sent` и известный `dropped/rejected` там, где
  протокол предоставляет основание; не называть IRC write подтверждённой
  доставкой пользователю.
- Изолировать Twitch supervisor от panic или неожиданного завершения и обеспечить
  наблюдаемое восстановление owner-задачи либо явный terminal status.
- Добавить безопасную диагностику: размер очереди, reconnect generation и
  причина отказа без логирования текста или token.

### Проверки P2

- Burst сообщений соблюдает выбранные интервалы и порядок; cancel/shutdown
  корректно освобождают ожидающих отправителей.
- Переполнение очереди возвращает стабильную typed error и не теряется как
  успешная доставка.
- Транспортный сбой во время очереди имеет явно проверенную политику для
  неотправленных и неоднозначно отправленных элементов.
- Panic или неожиданное завершение фоновой задачи не оставляет Twitch runtime
  навсегда без supervisor.

## Риски и решения, требующие утверждения

- Библиотека самостоятельно управляет background tasks и клонируемыми handles;
  неправильное хранение клона способно нарушить Disconnect/Restart.
- Автоматический reconnect библиотеки нельзя одновременно дублировать старым
  supervisor backoff: должен остаться один владелец повторного соединения.
- Статус Connected требуется вывести из фактического состояния канала. Если API
  библиотеки не даёт достаточного устойчивого сигнала, адаптер должен опираться
  на входящие JOIN/USERSTATE-события и тестируемую state machine.
- Переход на Helix Send Chat Message API рассматривается отдельно, если
  потребуется серверное `is_sent/drop_reason`, современный OAuth lifecycle или
  отказ Twitch от IRC.

## Критерии готовности направления

- P1 и P2 завершены отдельными проверенными tasks без смешивания их diff.
- Transport lifecycle и повторный JOIN принадлежат `twitch-irc`, а приложение
  сохраняет один явный owner настроек, статуса и исходящей доставки.
- Потеря сети, серверный RECONNECT, неверная авторизация, burst сообщений и
  shutdown не требуют перезапуска приложения.
- UI не сообщает Connected до подтверждённого входа и не сообщает delivered
  только на основании записи байтов в сокет.
- Неожиданное завершение дочерней задачи не оставляет Twitch без наблюдаемого
  статуса и пути восстановления.
- Документация интеграции описывает фактические лимиты частоты, очередь и смысл
  отображаемых статусов.

## Outcome

Самописный socket lifecycle заменён `twitch-irc` 6.1.1. Подключение считается
готовым только после подтверждённого JOIN; временные обрывы и `RECONNECT`
восстанавливаются без перезапуска приложения. Один runtime owner управляет
Stop, Restart, сменой настроек и shutdown без восстановления устаревшего
клиента. Исходящая доставка использует ограниченную FIFO-очередь, pacing и
наблюдаемые typed-результаты ошибок.
