# ROADMAP-109 — Качество вывода через THX Spatial Audio

## Проблема и цель

При выборе «Динамики (THX Spatial)» пользователь слышит сильное искажение и
звенящий звук. В микшере Razer для TTSBard выбран THX Spatial Audio, для
TTSVoiceWizard — стерео. Влияние этого различия ещё не проверено.

Цель — установить причину и обеспечить чистый вывод через THX, сохранив
работоспособность обычных устройств и независимого вывода в виртуальный микрофон.
Субъективное качество требует проверки на устройстве пользователя: отсутствие
ошибок в логе или успешная сборка не подтверждают устранение искажений.

## Исходные факты и гипотеза

На момент исследования Cargo.lock фиксирует rodio 0.19.0 и cpal 0.15.3.
До диагностики оба пути в `src-tauri/src/audio/player.rs` — `open_sink_on_device` и
`open_sink_on_device_pcm` — использовали `OutputStream::try_from_device`, то есть
стандартную конфигурацию устройства. Основное PCM-воспроизведение вызывает
общий helper из `src-tauri/src/playback.rs`.

В [cpal issue #892](https://github.com/RustAudio/cpal/issues/892) описаны сильные
искажения на Windows при выборе Razer 7.1, которые отсутствуют на обычном
High Definition Audio Device. Автор сообщает, что отключение surround не
помогло, но смена формата потока с f32 на i32 устранила проблему.
[Комментарий с обходом](https://github.com/RustAudio/cpal/issues/892#issuecomment-2364194193).

Первоначально это была гипотеза совместимости формата с драйвером.
Issue закрыта с предложением проверить новую rodio после переработки pipeline;
подтверждения исправления в обсуждении нет.
[Комментарий сопровождающего](https://github.com/RustAudio/cpal/issues/892#issuecomment-3639082824).
Пользователь подтвердил: i32 устраняет звон на его THX и нормально работает
через виртуальный кабель. Это подтверждает рабочий обход на проверенной системе,
но не устанавливает точную причину сбоя f32 и не гарантирует совместимость
всех драйверов. Обновление зависимостей сейчас не требуется для выбранного обхода.

## План выполнения

### P0 — Воспроизводимость и диагностика

1. Зафиксировать версии приложения, Windows и драйвера THX, выбранный выход,
   режим Razer и включённые DSP-эффекты. Использовать один аудиофрагмент,
   неизменную громкость и выключенный второй выход для первого сравнения.
2. Добавить логирование имени устройства, стандартной конфигурации и
   поддерживаемых диапазонов: sample format, частота, число каналов, buffer size.
   Отдельно писать фактически открытый формат и ошибки создания потока.
   Не писать текст синтеза, содержимое аудио или секреты; не логировать из callback.
3. Сравнить THX в режимах Spatial и Stereo с прямым физическим выходом.
   Проверить тестовый звук, TTS и PCM-preview; записать время и результат на слух.

Разрешённый первоначальный scope: `src-tauri/src/audio/player.rs`.
Если для диагностики требуется расширение scope, определить его до реализации.

### P1 — Управляемая проверка i32

1. Добавить временный диагностический выбор `default` / `i32` через переменную
   окружения, без нового постоянного UI и persisted settings. Имя и допустимые
   значения зафиксировать в локальном task перед реализацией.
2. Применять выбор в общем открытии потока для encoded и PCM-путей.
   Для i32 искать поддерживаемую конфигурацию с теми же частотой и числом
   каналов, что у стандартной. Не менять одновременно частоту, DSP и каналы.
3. При отсутствии совместимой конфигурации или ошибке открытия явно сообщать
   причину. В диагностическом режиме не делать скрытый fallback в default,
   иначе сравнение окажется недостоверным. Не переключаться на другое устройство.
4. Повторить один фрагмент в default и i32 на THX; зафиксировать фактические
   форматы, результат на слух и, по возможности, запись loopback для сравнения.

Разрешённый первоначальный scope: общий stream helper и colocated tests в
`src-tauri/src/audio/player.rs`. PCM-буферы приложения остаются f32:
эксперимент меняет формат вывода устройства, не внутренний DSP-контракт.

### P2 — Постоянная общая настройка формата вывода

Пользователь выбрал один переключатель для всех выходов приложения.
Раздельные настройки динамика и виртуального микрофона не добавляются.
Default остаётся исходным значением для новых и старых конфигураций;
i32 включается явно пользователем. Внутренние PCM, DSP и микширование остаются f32.

#### Оформление в UI

- Разместить компактную карточку в «Аудио → Устройства», **под обеими карточками
  устройств и перед кнопкой обновления**. Отдельную вкладку не создавать.
- Использовать существующие `setting-section`, `setting-row`, `input-with-action`
  из `src/components/audio/AudioDevicesTab.vue`: тот же фон, рамка, радиусы,
  отступы и select. Без акцентной/предупреждающей плашки и заголовка «тест THX».
- Название поля: **«Формат вывода»**.
- Пункты: **«По умолчанию»** и **«32-битный целочисленный (i32)»**.
  В английском интерфейсе: `Output format`, `Default`, `32-bit integer (i32)`.
  «Автоматически» и «Дефолтный» не использовать.
- Спокойная короткая подпись под полем: **«Для всех аудиовыходов.
  При искажениях попробуйте i32.»** Без цветной info-box для постоянной подсказки.
- Рядом с названием — иконка информации с доступной кнопкой/подсказкой,
  `title` и `aria-label`. Пояснение: «По умолчанию используется стандартный
  формат устройства. i32 меняет только формат передачи звука устройству;
  эффекты и DSP работают как прежде.»
- Под полем при отложенном применении показать **«Применится после остановки
  текущего звука»**. Не показывать уведомление об успешном изменении на каждый выбор.
- В узкой панели разрешить перенос строки/подписи, сохранить читаемость
  длинного пункта i32, доступность с клавиатуры, обе темы и отсутствие overflow.

#### Поведение и сохранение

1. Добавить в аудиоконфигурацию валидируемое значение `default | i32`,
   со значением default при отсутствии поля. Сохранять через существующий
   SettingsManager и публиковать обычное событие изменения настроек.
2. Панель читает подтверждённую настройку из общего источника settings.
   Удалить временный session override и переменную `TTSBARD_OUTPUT_FORMAT`
   из продуктового пути: сохранённая настройка становится единственным
   источником выбранного формата. Обновить инструкции диагностики.
3. Смена формата не прерывает и не пересоздаёт активный поток. Новое значение
   применяется при следующем открытии потока; остановка и новый запуск
   гарантируют применение. Для подписи отложенного применения использовать
   существующее состояние воспроизведения, проверить также preview и SoundPanel;
   не обещать, что уже открытый поток сменит формат при следующей фразе.
4. При ошибке сохранения оставить прежнее подтверждённое значение и показать
   локализованную ошибку. На время запроса блокировать повторное изменение,
   учитывать обновления settings извне и не принимать устаревший async-результат.
5. При неподдерживаемом i32 или ошибке открытия сохранить понятную ошибку
   с устройством и причиной. Не делать скрытый fallback и не менять выбранное
   устройство. Другой независимый выход может продолжить воспроизведение.
   Возможность вернуться к «По умолчанию» всегда доступна.

#### Порядок реализации

Разбить следующий этап на два ограниченных implementation concern:

1. Backend/config: persistence, runtime source of truth, совместимость старых
   settings, переход с временного override, сохранение strict i32 пути.
2. UI: размещение карточки, названия/переводы/подсказка, чтение settings,
   ошибки и корректная подпись применения. Эталон — существующие карточки
   AudioDevicesTab, без перестройки остальных аудионастроек.

Перед каждым task зафиксировать baseline и точные разрешённые пути в `.work/ai/`;
не менять родио/cpal, эффекты, DSP или маршрутизацию аудио в рамках P2.
Этап реализован после согласования roadmap пользователем.

### P3 — Регрессии и завершение

Проверить THX (Spatial/Stereo), обычное стереоустройство и VB-Cable:
encoded/PCM, тестовый звук, preview, очередь, pause/resume/seek/stop,
смену устройства и dual output. В dual output каждый поток должен учитывать
возможности своего устройства. Проверить неподдерживаемый i32 и ошибку открытия.
Автотестами покрыть выбор конфигурации и отсутствие скрытого fallback;
аудиокачество проверить вручную.

Команды приёмки для Rust выполняются через Windows-обёртку:

```powershell
./scripts/cargo.ps1 test --manifest-path src-tauri/Cargo.toml audio::player
./scripts/cargo.ps1 check --manifest-path src-tauri/Cargo.toml
./scripts/build.ps1 -Mode debug
./scripts/check-docs.ps1
```

Фильтр тестов уточнить после появления colocated tests. Полная debug-сборка
нужна для ручного аппаратного сравнения; frontend-проверки добавляются только
при изменении frontend.

## Процесс и критерии готовности

### Состояние P0–P2 на 2026-09-28

P0/P1 реализованы: диагностика конфигураций, strict i32 через CPAL с прежними
rodio mixer и Sink. Пользователь подтвердил устранение звона THX и нормальный
вывод через виртуальный кабель. Полная матрица регрессий остаётся открытой.

P2 реализован в исходниках: карточка под обоими устройствами, «Формат вывода»,
«По умолчанию» / «32-битный целочисленный (i32)», спокойная подпись и подсказка.
Общий выбор сохраняется в `settings.json` в `audio.output_format` (`default | i32`).
Отсутствующее поле читается как default; неизвестное значение отклоняется serde.
SettingsManager атомарно сохраняет поле и обновляет общий кэш только после успеха.
Каждый новый поток читает этот кэш; отдельного runtime override нет.
`TTSBARD_OUTPUT_FORMAT` больше не управляет продуктовым выводом.

Смена выбора не пересоздаёт открытый поток. Статус отложенного применения
определяется по открытым потокам старого режима, включая TTS, preview,
тестовый звук и SoundPanel; UI обновляет статус раз в секунду и очищает таймер
при закрытии вкладки. Доступен возврат к default при ошибке i32.

Ограничение rodio 0.19 сохраняется: при ошибке открытия default она может
подобрать другой формат. Лог не выдаёт запрошенный default за фактический формат;
только strict i32 подтверждает открытый формат. Поддерживаемый buffer size —
диапазон; фактическая длина буфера драйвера не измеряется.
Диагностические записи — INFO в `%APPDATA%\ttsbard\logs\ttsbard.log` при
включённом файловом логировании и разрешающем фильтре.

Реализацию выполнил Codex с разрешения пользователя после сбоя OpenCode.
Проверены vue-tsc без генерации сборки, IPC, locale/settings parity,
frontend-тесты и форматирование. JSON fixtures дополнены вручную в соответствии
с новым полем DTO; Rust-регенерация пока не выполнялась.
Добавлены Rust-тесты старого формата settings, persistence/cache и ошибки записи.
Сборка и Rust-тесты не запускались по указанию пользователя «только реализация».
Визуальная runtime-проверка UI, перезапуск приложения с сохранённым выбором
и полная аппаратная матрица P3 отдельно не документировались. После реализации
пользователь подтвердил «работает» и явно запросил закрытие roadmap.
Это подтверждение рабочего результата на его системе; оно не означает,
что Codex выполнил все перечисленные сборочные и аппаратные проверки.

## Outcome

- Пользователь подтвердил устранение звона на THX при i32 и нормальную работу
  виртуального кабеля с тем же форматом; после постоянного оформления подтвердил
  работу результата и принял завершение направления 2026-09-28.
- В «Аудио → Устройства» под двумя карточками выходов находится общий выбор
  «Формат вывода»: «По умолчанию» / «32-битный целочисленный (i32)».
  Выбор сохраняется в `audio.output_format` и восстанавливается при запуске.
  Старые settings без поля используют default.
- Новые потоки читают общую настройку SettingsManager. Активный поток не
  пересоздаётся при смене выбора; UI показывает отложенное применение.
  Неподдерживаемый i32 возвращает ошибку без скрытого fallback.
- Внутренняя обработка PCM, эффекты и DSP остаются f32. Точная причина сбоя
  THX в стандартном формате не установлена; подтверждён обход совместимости.
- Пройдены TypeScript, settings/IPC/locale parity, проверка документации и
  93 frontend-теста. Сборку и Rust-тесты Codex не запускал по указанию пользователя.
- Инструкция постоянной настройки добавлена в
  [руководство виртуального аудиокабеля](../../user/virtual-audio-cable.md#формат-вывода-ttsbard).

Реализацию разбить на локальные tasks P0 и P1 в `.work/ai/<work-id>/`:
baseline → ограниченные пути → DeepSeek через OpenCode → независимый review.
Не включать существующие пользовательские изменения. Логи, prompts и записи
сравнения хранить в `.work/ai/`, коммиты выполнять только с явным одобрением.

Направление завершено, когда рабочий обход проверен на THX пользователя,
общая настройка оформлена по P2 и сохраняется после перезапуска, старые settings
открываются с default, обычный вывод и виртуальный микрофон проходят регрессии,
эффекты/DSP не изменяются, а временные override и тексты диагностики заменены
постоянным контрактом. Точная причина драйверного сбоя может оставаться неизвестной;
не обозначать подтверждённый обход как доказанное исправление драйвера.
