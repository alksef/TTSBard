# ROADMAP-047 — Очередь задач озвучивания

**Статус:** `completed` — первая неперсистентная версия реализована 24 июля 2026 года

## Проблема

Сейчас `speak_text` выполняет весь pipeline до добавления фразы в очередь
воспроизведения:

1. разбирает prefix-флаги и применяет препроцессор;
2. при необходимости ждёт AI-коррекцию;
3. ждёт ответ TTS-провайдера;
4. декодирует и обрабатывает аудио;
5. сохраняет аудиокэш;
6. передаёт готовый PCM в `PlaybackManager`.

`PlaybackManager` принимает только готовый `QueuedPhrase { text, audio }`. Пока
провайдер не вернул аудио, сообщение отсутствует в playback state и не видно в
окне управления. В обычном режиме редактор дополнительно ждёт завершения
`speak_text` перед автоочисткой. Быстрые режимы освобождают UI раньше, но не
создают наблюдаемую задачу в очереди.

Такой порядок связывает скорость редактора с сетью и не позволяет надёжно
показать генерацию, ошибку или повторную отправку конкретного сообщения.

## Целевое поведение

Нажатие `Enter` означает локальное принятие сообщения приложением, а не
завершение синтеза:

1. backend валидирует сообщение и наличие места в очереди;
2. создаёт задачу с устойчивым `job_id`;
3. возвращает frontend подтверждение приёма;
4. frontend очищает редактор и выполняет действие быстрого режима;
5. задача немедленно появляется в окне очереди;
6. фоновый worker выполняет TTS pipeline и передаёт готовое аудио существующему
   `PlaybackManager`;
7. при ошибке исходный текст остаётся в failed-задаче для retry;
8. существующая история фраз обновляется по прежнему контракту после успешной
   обработки.

```text
Editor
  │ submit_speech(original_text)
  ▼
Speech job queue
  Queued → Generating → Ready → Playing → Completed
                └────────────→ Failed
                                  │
                         queue = Blocked
                                  │ explicit retry / skip
                                  ▼
                         Queued / Cancelled
                              ▼
                    PlaybackManager (готовый PCM)
```

## Разделение ответственности

### Speech job queue

Новый orchestration-слой владеет сообщением до готовности аудио:

- сохраняет FIFO-порядок пользовательских отправок;
- хранит состояние и ошибку каждой попытки;
- выполняет preprocessing, AI, TTS, эффекты и запись кэша;
- поддерживает retry failed-задачи;
- публикует изменения состояния для UI;
- передаёт готовый PCM нижнему playback-слою.

### PlaybackManager

Существующий `PlaybackManager` остаётся ответственным за готовое аудио:

- текущий `rodio::Sink`;
- pause, resume, stop и repeat;
- очередь готового PCM;
- переключение на следующую готовую фразу;
- недавний аудиокэш для точного replay.

История сообщений не используется как runtime-очередь: она дедуплицирует
одинаковые фразы и не представляет отдельные попытки, порядок и transient
состояния.

## Модель задачи

Минимальная задача должна содержать:

```text
job_id
original_text
spoken_text?
status
error?
attempt
created_at
provider / voice snapshot
pipeline settings snapshot
prefix flags
cache_key?
```

Базовые состояния:

- `queued` — принята и ожидает worker;
- `generating` — выполняется preprocessing/AI/TTS/audio pipeline;
- `ready` — PCM готов и ожидает воспроизведения;
- `playing` — передана активному playback;
- `paused` — воспроизведение приостановлено;
- `failed` — pipeline завершился ошибкой, доступен retry;
- `completed` — воспроизведение завершено;
- `cancelled` — задача отменена пользователем.

На уровне всей очереди требуется состояние `blocked`. Ошибка принятой задачи
останавливает обработку следующих задач: они сохраняют позиции и остаются
`queued`, пока пользователь явно не разрешит продолжение.

Необязательно хранить все состояния в одном Rust enum: `paused` относится к
playback, но публичный DTO должен давать UI единую и непротиворечивую картину.

## История сообщений вне scope

Первая версия не меняет формат, момент записи и UI существующей истории фраз.
Она продолжает хранить успешно обработанный текст вместе с provider, voice и
`cache_key`; autocomplete-история также работает по текущему контракту.

`original_text` и `spoken_text` одновременно существуют только внутри
`SpeechJob`. Это позволяет показать детали активной задачи и выполнить retry,
не создавая два сообщения в `phrase_history.json` и не требуя миграции истории.
Отдельное сопоставление введённого и фактически озвученного текста может быть
добавлено позже как самостоятельная функция.

Failed-задача не записывается в историю успешных фраз. Пока активная очередь
неперсистентна, восстановить её после перезапуска приложения нельзя.

Retry активной failed-задачи не создаёт новую позицию в конце очереди: он
увеличивает `attempt`, сохраняет `job_id` и повторяет ту же позицию. Это не даёт
более поздним сообщениям обойти проблемное сообщение.

## Политика остановки при ошибке

Очередь работает в fail-closed режиме. Любая ошибка принятой задачи до успешной
передачи готового аудио в playback останавливает продвижение FIFO:

- проблемная задача получает `failed` и остаётся на своей позиции;
- очередь получает `blocked`;
- следующие задачи не запускают preprocessing, AI или TTS;
- ранее начатое воспроизведение может корректно завершиться;
- ни одна задача после failed-позиции не передаётся в playback автоматически.

Разблокировать очередь можно только явным действием:

- **Retry** — повторить ту же задачу на той же позиции;
- **Изменить и повторить** — исправить исходный текст проблемной задачи и
  повторить её без перестановки остальных сообщений;
- **Пропустить/отменить** — пометить задачу `cancelled` и продолжить со
  следующей; UI должен явно предупреждать, что пользователь сознательно меняет
  последовательность озвученных сообщений.

Автоматический skip, автоматический переход к следующему сообщению и перенос
failed-задачи в конец запрещены. Иначе видимый порядок отправки перестаёт быть
гарантированным порядком речи.

Текущие `input_history.json`/ngrams для autocomplete и `phrase_history.json`
решают разные задачи. Их нельзя неявно объединять без отдельного решения о
миграции формата.

## Snapshot настроек

При принятии задачи необходимо зафиксировать настройки, влияющие на результат:

- выбранный provider и voice;
- AI toggle, provider и prompt;
- preprocessing/prefix-флаги;
- audio effects, DSP и boundary cleanup;
- конфигурацию speaker/virtual mic, если принято решение сохранять маршрут
  вывода на момент отправки.

Без snapshot отложенная задача может обработаться голосом или эффектами,
выбранными уже после её отправки. Отдельно нужно решить, использует ли ручной
retry исходный snapshot или актуальные настройки; рекомендуемый default —
исходный snapshot с отдельным действием «сгенерировать с текущими настройками».

Prefix-флаги должны принадлежать задаче. Текущая общая mutable-пара флагов в
`AppState` небезопасна для нескольких принятых или параллельно выполняемых задач.

## Порядок и конкурентность

Первая версия использует один FIFO-worker синтеза. Это гарантирует порядок, не
создаёт параллельную нагрузку на провайдера и естественно останавливается на
первой ошибке.

Worker может готовить следующую фразу, пока предыдущая воспроизводится. Это
prefetch без нарушения порядка. Параллельный синтез нескольких задач допускается
только после появления ordered slots: результаты могут приходить в другом
порядке, но передача в playback обязана сохранять порядок отправки. Любой
будущий parallel prefetch требует ordered commit barrier: failed slot блокирует
выдачу всех более поздних готовых результатов.

## Backend API и события

Предполагаемый внешний контракт:

- `submit_speech(text) -> AcceptedJob { job_id }`;
- `retry_speech_job(job_id)`;
- `skip_speech_job(job_id)` или эквивалентное явное подтверждение отмены;
- `cancel_speech_job(job_id)`;
- `get_speech_queue_state() -> SpeechQueueStateDto`;
- событие `speech-queue-changed` после каждого наблюдаемого перехода.

`submit_speech` возвращает ошибку до очистки редактора, если текст невалиден,
очередь переполнена или backend не может гарантировать принятие. Ошибки после
принятия записываются в job state и доставляются событием, а не rejected
результатом уже завершившегося IPC-вызова.

Существующий `queue-changed` также необходимо исправить или заменить: сейчас
добавление готовой фразы позади играющей не всегда немедленно уведомляет окно,
поскольку событие испускается при завершении playback, а не на каждом enqueue.

## Изменения окна управления

`PlaybackStateDto.queue: Vec<String>` недостаточен. Окно должно получать
элементы с `id`, текстом и состоянием и показывать как минимум:

- текущую генерацию;
- готовую/играющую фразу;
- ожидающие задачи в пользовательском порядке;
- failed-задачи с краткой ошибкой и действием retry;
- общий индикатор остановленной очереди и причину блокировки;
- отмену ожидающей или failed-задачи.

Статусы должны быть пользовательскими (`Генерация`, `Готово`, `Играет`,
`Ошибка`), а не прямым выводом Rust enum на английском.

## Персистентность

Первая итерация может держать активную очередь в памяти:

- сбой провайдера восстанавливается через `failed → retry`;
- после перезапуска failed/queued-задачи и их исходный текст не восстанавливаются;
- автоматическое восстановление порядка незавершённых задач не гарантируется.

Персистентный job journal (`speech_queue.json` или другой storage) является
отдельным этапом. Он нужен, если продукт должен автоматически восстанавливать
`queued`/`failed` после аварийного завершения приложения. История сообщений не
заменяет такой journal.

## Этапы реализации

1. Ввести модель `SpeechJob`, FIFO state machine и тесты переходов без UI.
2. Добавить быструю команду принятия задачи и последовательный worker поверх
   существующего TTS pipeline.
3. Перенести prefix-флаги и влияющие настройки в job snapshot.
4. Подключить готовые задачи к `PlaybackManager`, сохранив текущие
   pause/resume/stop/replay контракты.
5. Перевести окно управления на typed job DTO, статусы, retry и cancel.
6. Перевести `InputPanel` на очистку и действие quick mode после подтверждения
   локального принятия, а не после завершения синтеза.
7. Проверить error, retry, stale events, queue full, смену вкладки редактора,
   смену настроек во время ожидания и закрытие приложения.
8. Отдельно решить необходимость персистентного восстановления активной очереди.

## Критерии готовности первой версии

- сообщение появляется в окне очереди сразу после принятия;
- существующая история фраз сохраняет текущий формат и поведение;
- editor не ждёт сеть перед очисткой и возвратом фокуса;
- несколько сообщений можно отправить подряд, порядок воспроизведения совпадает
  с порядком отправки;
- provider error не удаляет исходный текст и допускает retry;
- ошибка останавливает очередь на проблемной позиции, следующие сообщения не
  генерируются и не воспроизводятся;
- retry сохраняет позицию и порядок, а skip требует явного действия;
- одинаковые сообщения являются разными job attempts независимо от
  дедупликации существующей истории;
- смена provider/voice/effects после отправки не меняет уже принятую задачу;
- cancelled job разблокирует последующие задачи только после явного решения
  пользователя;
- готовый cache replay не обращается к TTS-провайдеру;
- окно обновляется на каждом переходе без polling и запоздалого enqueue event;
- существующие history-файлы не требуют миграции.

## Результат реализации

Первая версия реализована поверх существующего TTS и playback pipeline:

- `submit_speech` подтверждает локальное принятие и немедленно возвращает устойчивый `job_id`;
- один wake-driven worker обрабатывает immutable snapshot настроек и сохраняет FIFO-порядок;
- fail-closed state machine поддерживает retry, skip/cancel и блокировку на ошибочной позиции;
- `PlaybackManager` сохраняет job identity и per-phrase output route до завершения;
- окно playback показывает typed job DTO, статусы, ошибки и явные Retry/Skip/Cancel;
- `InputPanel` очищает только неизменённую исходную вкладку после acceptance, не ожидая сеть;
- история фраз и cache replay сохраняют прежние контракты, активная очередь остаётся в памяти.

Проверки завершения: 262 frontend-теста, production frontend build, `cargo fmt --check` и
компиляция всех Rust test targets. Запуск Rust test binary на рабочей Windows-машине
ограничен внешней ошибкой нативной DLL `STATUS_ENTRYPOINT_NOT_FOUND`; сами test targets
компилируются без ошибок.

## Открытые решения

- Должен ли retry использовать исходный snapshot или актуальные настройки?
- Нужно ли сохранять активную очередь между перезапусками уже в первой версии?
- Должен ли `stop` отменять только playback, текущую job целиком или также
  автоматически переходить к следующей?
- Нужны ли отдельные действия «Повторить аудио» и «Сгенерировать заново» прямо в
  плавающем окне, либо второе действие остаётся в истории сообщений?
