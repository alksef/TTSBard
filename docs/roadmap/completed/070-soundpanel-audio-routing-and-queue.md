# ROADMAP-070 — Маршрутизация и очередь SoundPanel

## Проблема

Звуки SoundPanel должны идти по тому же пользовательскому маршруту, что и
обычная озвучка: в включённые динамики и в настроенный виртуальный микрофон.
Их нельзя отправлять только на системное устройство по умолчанию.

Несколько быстрых нажатий SoundPanel запускают несколько независимых
воспроизведений. Звуки накладываются друг на друга, что делает панель
непредсказуемой для стрима и мешает разборчивости.

## Цель

SoundPanel получает собственный последовательный playback-путь:

1. каждый звук использует актуальные настройки аудио и маршрутизируется в те
   же каналы, что TTS;
2. звуки одной SoundPanel воспроизводятся строго FIFO, без наложения;
3. очередь SoundPanel изолирована от очереди TTS: звук панели не прерывает,
   не задерживает и не меняет порядок речевых фраз, и наоборот.

Одна общая очередь аудио не используется: она задерживала бы короткие эффекты
за длинной речью либо задерживала бы речь за эффектами. Общим остаётся только
слой выбора выходных устройств.

```text
SoundPanel key / click
  → SoundPanel queue (FIFO)
  → audio-settings snapshot
  → speaker output + virtual-mic output
  → next sound only after both active outputs finish

Editor submit
  → Speech job queue
  → PlaybackManager
  → independent TTS playback
```

## Продуктовый контракт

1. При принятии sound binding фиксируется снимок AudioSettings:
   - динамики добавляются, только если speaker_enabled включён;
   - отсутствие speaker_device означает системное устройство вывода по
     умолчанию;
   - виртуальный микрофон добавляется, только если указан virtual_mic_device;
   - для каждого выхода используется его собственная громкость.
2. Один sound binding декодируется отдельно для каждого включённого выхода.
   Ошибка одного устройства логируется и не отменяет запуск второго.
3. Одна SoundPanel-очередь принимает нажатия в порядке поступления и запускает
   следующий звук только после завершения всех успешно открытых выходов
   предыдущего.
4. Если ни один выход не удалось открыть либо файл невозможно декодировать,
   элемент считается завершённым с ошибкой, worker продолжает следующий
   элемент; очередь не блокируется навсегда.
5. Первая версия очереди — runtime-only: без persistence, UI списка,
   pause/resume и ручного управления. После перезапуска она пуста.
6. Не изменяются формат soundpanel_bindings.json, наборы/слои, поведение окна,
   глобальный Intercept и TTS PlaybackManager.

## Архитектурные границы

- SoundPanelState владеет отдельным sender и worker lifecycle очереди.
- Очередь хранит только минимум для исполнения: путь файла и неизменяемый
  снимок AudioSettings; пользовательский текст и TTS-метаданные в неё не
  попадают.
- Worker единолично владеет активным воспроизведением SoundPanel. Команда
  sp_play_binding только валидирует binding, создаёт snapshot и ставит элемент
  в очередь, не выполняя блокирующее аудио в Tauri-команде.
- Низкоуровневое открытие stream/sink остаётся в soundpanel::audio; оно
  переиспользует общий resolver аудиоустройств, но не подключается к
  PlaybackManager, чтобы не смешивать control state и очередь речи.

## Этапы

### P1 — Общая маршрутизация аудиоканалов

**Завершён 2026-08-14.**

1. Убрать default-only вывод SoundPanel.
2. Превратить AudioSettings в два независимых OutputConfig по тем же правилам,
   что используются для TTS.
3. Создавать stream/sink для всех доступных выходов до ожидания завершения;
   удерживать stream до конца playback.
4. Изолировать ошибки устройства и decoder между выходами.

**Проверка:** unit-тесты выбора выходов для speaker+mic, только mic и только
speaker; ручной запуск звука слышен в обоих настроенных каналах.

### P2 — Отдельный FIFO-worker SoundPanel

**Завершён 2026-08-14.** Реализована runtime-only bounded FIFO-очередь
ёмкостью 16 элементов. Один worker запускается в setup::init_app, использует
общий shutdown token и последовательно обслуживает sp_play_binding и
sp_test_sound. Ошибочный элемент не блокирует следующий; TTS SpeechQueue и
PlaybackManager не затронуты.

1. Ввести bounded runtime-only очередь и один wake-driven worker.
2. Передавать в worker binding path и snapshot аудионастроек.
3. Перевести sp_play_binding и sp_test_sound на enqueue без ожидания
   завершения звука.
4. Продвигать worker после success и после ошибки, не оставляя очередь
   заблокированной.
5. Останавливать worker штатно при shutdown приложения.

**Проверка:** быстрое нажатие трёх разных биндингов запускает их в порядке
нажатия и без overlap; ошибка первого файла или устройства не препятствует
второму; TTS в это время сохраняет свою независимую очередь и playback.

### P3 — Наблюдаемость и политика переполнения

Очередь ограничена 16 элементами; при переполнении новое нажатие отклоняется
с ошибкой. Безопасные логи фиксируют ключ binding, путь аудиофайла, устройство
и ошибку воспроизведения. Открытым остаётся только решение о runtime-индикаторе
очереди в интерфейсе.

1. Решить, нужен ли компактный runtime-индикатор очереди в SoundPanel.

## Риски и открытые решения

- **Политика overflow:** для sound effects допустимо отклонять новые нажатия,
  но точный лимит и UX сообщения нужно выбрать перед P2.
- **Stop/skip:** не входят в первую итерацию. Если появятся, должны влиять
  только на SoundPanel worker и не останавливать TTS.
- **Фактическое одновременное воспроизведение TTS и SoundPanel:** это
  намеренная изоляция очередей; оба пути могут обращаться к одному устройству,
  поэтому финальная ручная проверка обязана покрыть драйверы пользователя.

## Критерии завершения

- SoundPanel использует динамики и виртуальный микрофон согласно актуальным
  настройкам аудио.
- Два канала одного sound binding стартуют до ожидания его завершения.
- Два sound binding не накладываются, включая быстрые повторные нажатия.
- Ошибка одного output или одного queue item не останавливает последующие
  sound bindings.
- TTS queue и PlaybackManager не меняют свой контракт и не получают
  SoundPanel-элементы.

## Outcome

2026-08-17. P1 (общая маршрутизация speaker+virtual-mic) и P2 (runtime-only
bounded FIFO-очередь, изолированная от TTS SpeechQueue) завершены 2026-08-14
и находятся в master.

P3: пользователь решил, что runtime-индикатор очереди в SoundPanel пока не
нужен — очередь на 16 элементов с отклонением при переполнении достаточна без
визуализации. Если индикатор станет нужен, это новый roadmap-item, а не
переоткрытие 070.

Не выполнено: финальная ручная проверка одновременного TTS + SoundPanel на
драйверах пользователя (см. риски); автотестами не покрывается.

Stop/skip не реализованы намеренно и остаются вне scope.
