# ROADMAP-053 — Настройка ожидания и повторов Silero

## Outcome

В `tts.telegram` добавлены скрытые настройки
`synthesis_response_timeout_ms` и `download_retry_delay_ms` с defaults
`10000`/`1000` миллисекунд и нормализацией до диапазонов
`1000…120000`/`100…10000`. Старые конфиги получают defaults через serde, а
backend DTO и TypeScript-контракт сохраняют значения без добавления UI.

Один `SileroRuntimeSettings` snapshot с типизированными `Duration` передаётся в
оба пути синтеза: обычный speech queue/provider и прямой
`speak_text_silero`. Queue фиксирует значения при создании job snapshot;
Telegram bot helpers не читают глобальный конфиг. Response timeout и пауза
между пустыми скачиваниями больше не заданы локальными константами, при этом
максимум попыток остаётся равным трём и не вынесен в настройки.

Добавлена пользовательская справка по ручному редактированию
`%APPDATA%\ttsbard\settings.json`; изменения применяются после перезапуска.
`npm run build`, `cargo test --no-run`, `cargo check` и проверка документации
проходят. Запуск Rust test binary в текущем checkout блокируется существующей
локальной native-ошибкой `STATUS_ENTRYPOINT_NOT_FOUND`; тесты успешно
компилируются.

## Контекст

ROADMAP-052 сокращает ожидание ответа Silero до 10 секунд и сразу преобразует
связанный текстовый отказ в стандартизированную ошибку приложения. Следующий
шаг — убрать эксплуатационные значения из жёстких констант и разрешить опытному
пользователю менять их вручную в `settings.json`, не добавляя пока новые
элементы UI.

Нужно различать три независимых параметра:

- время ожидания связанного аудио или текстового ответа после отправки запроса;
- пауза между повторными скачиваниями, если Telegram сохранил пустой файл;
- максимальное число попыток скачивания.

`download_retry_delay` не является сетевым timeout: увеличение этого значения
только откладывает следующую попытку после пустого результата.

## Рекомендуемый контракт

Использовать существующий раздел `tts.telegram`, который уже хранит настройки
Telegram TTS для Silero:

```json
{
  "tts": {
    "telegram": {
      "synthesis_response_timeout_ms": 10000,
      "download_retry_delay_ms": 1000
    }
  }
}
```

| Ключ | Default | Допустимый диапазон | Назначение |
|---|---:|---:|---|
| `synthesis_response_timeout_ms` | `10000` | `1000…120000` | Ожидание связанного audio/text reply после отправки текста |
| `download_retry_delay_ms` | `1000` | `100…10000` | Пауза после пустого скачанного файла перед следующей попыткой |

Значения вне диапазона нормализуются до ближайшей границы с безопасным warning,
а старый `settings.json` без ключей получает defaults через `serde(default)`.
На первом этапе ручное изменение применяется после перезапуска приложения:
settings загружаются и кэшируются при старте.

### Рассмотренные варианты ключей

1. **`tts.telegram.*` — выбранный вариант.** Совпадает с существующей моделью
   хранения `api_id`, proxy mode и голосов; не требует параллельного раздела.
2. `tts.silero.*` — понятнее по названию провайдера, но дублирует уже существующий
   `tts.telegram` и потребует миграции либо двух источников истины.
3. `tts.telegram.advanced.*` — визуально отделяет скрытые параметры, но добавляет
   вложенную DTO-структуру без практической пользы для двух полей.

Общий `tts.timeout_ms` не использовать: HTTP-провайдеры имеют другие этапы и
семантику timeout, поэтому одно значение создало бы ложную унификацию.

## Этапы

### P0 — Ошибка лимита и короткий default

Завершён в ROADMAP-052:

- текстовый отказ Silero относится к исходящему запросу по peer, порядку ID и
  точному `reply_to` и немедленно преобразуется в стандартную limit/generic
  ошибку без передачи исходного текста;
- link preview не мешает распознать связанный непустой текст;
- default ожидания снижен с 30 до 10 секунд;
- correlation-логи не содержат полный текст ответа.

### P1 — Persisted hidden settings

1. Добавить оба поля в `TelegramTtsSettings` с явными default-функциями.
2. Добавить валидацию диапазонов и backward-compatibility тест старого JSON.
3. Провести поля через backend DTO и TypeScript `TelegramTtsSettingsDto`, даже
   если UI их не показывает. Это обязательно, чтобы обычное сохранение настроек
   не удаляло вручную заданные значения.
4. Добавить reference-раздел с путём к `settings.json`, JSON-примером, единицами,
   диапазонами и требованием перезапуска.

### P2 — Единая runtime-конфигурация Silero

1. Ввести небольшой value object для runtime-настроек Silero вместо чтения
   глобального файла внутри Telegram bot helpers.
2. Передавать snapshot настроек в оба пути синтеза:
   - основной provider/queue через `SileroTts`;
   - прямую Tauri-команду `speak_text_silero`.
3. Использовать `Duration::from_millis` для response timeout и retry delay;
   убрать соответствующие жёсткие константы из `telegram/bot.rs`.
4. Логировать только итоговые числовые значения и безопасные IDs, без текста
   запроса или ответа.

### P3 — Политика повторов и live apply

Отдельно оценить после наблюдений, не включая автоматически в P1/P2:

- `download_max_attempts` с default `3` и диапазоном `1…10`;
- применение изменённых значений без перезапуска через общий settings cache;
- небольшой advanced UI, если ручное редактирование станет частым сценарием;
- отдельные таймауты `/speaker` и `/limits`, только если runtime-логи покажут
  реальную необходимость.

## Оценка реализации

P1 и P2 — средняя backend/full-stack задача примерно на 8–10 файлов: settings,
DTO conversions, TypeScript contract, Silero provider/runtime wiring, прямая
Telegram command и тесты. Архитектурно новый сервис не нужен; основная сложность
— не потерять скрытые поля при DTO round-trip и одинаково применить их в двух
путях синтеза.

Рекомендуемая декомпозиция — две отдельные реализации:

1. config schema, validation, DTO/TypeScript round-trip и документация;
2. runtime propagation в Silero provider, direct command и Telegram bot helpers.

## Проверка

- старый JSON без новых полей десериализуется с defaults;
- min/max и значения вне диапазона нормализуются предсказуемо;
- backend DTO round-trip и frontend settings object сохраняют скрытые поля;
- queue/provider и `speak_text_silero` используют одинаковый snapshot;
- тест с коротким response timeout подтверждает фактическое применение значения;
- тест повторной загрузки подтверждает настраиваемую задержку без реального sleep
  через выделенную чистую политику либо paused Tokio time;
- `npm test` и `npm run build` для изменения TypeScript-контракта;
- `cargo test --no-run` и `cargo check` из `src-tauri`;
- `./scripts/check-docs.ps1`.

## Условия завершения

- оба ключа сохраняются в `settings.json`, проходят DTO round-trip и применяются
  во всех путях Silero;
- defaults сохраняют 10 секунд ожидания и 1 секунду между download retries;
- невалидный ручной ввод не приводит к нулевому, бесконечному или чрезмерному
  ожиданию;
- документация однозначно объясняет единицы, диапазоны, область действия и
  необходимость перезапуска;
- фактический outcome и проверки внесены перед переносом item в `completed/`.
