# ROADMAP-079 — Затухание ошибки ручного подключения VTS в titlebar

## Контекст

ROADMAP-074 зафиксировал маппинг `desired × runtime → gray/green/red`, включая
«red при startup failure при сохранённом desired-running». После доработок
(`498663f`, `bcc6e28`, `e9a5fff`) иконка VTS в titlebar честно показывает
зелёный при успехе и красный при любой ошибке подключения — и красный теперь
**персистентен всегда**.

Практика показала, что персистентность нужна не всегда:

- **Автостарт** (`start_on_boot`): подключения не произошло, а пользователь
  мог и не открывать панель — красный должен оставаться, пока проблема не
  разрешена. Это единственный канал, через который пользователь узнаёт о
  сбое ожидаемого подключения.
- **Ручная попытка** (кнопки Connect/Restart в панели): пользователь только
  что нажал кнопку и видит ошибку на самой панели. Вечный красный в
  titlebar после этого — шум: инициатор и так в курсе.

Для сравнения: у Twitch красный затухает в серый примерно через секунду, но
это **побочный эффект** устройства server-loop (при failed start клиент не
сохраняется, и следующий poll-тик перезаписывает `Error → Disconnected`), а
не осознанный дизайн. Копировать эту механику не предлагается: она не
различает причины ошибки и затухает слишком быстро, чтобы успеть заметить.

## Цель

Различать происхождение неуспешного подключения VTube Studio:

- ручная попытка — красный показывается ограниченное время (достаточное,
  чтобы заметить), затем иконка затухает в серый;
- автостарт — красный сохраняется до разрешения (успешное подключение,
  явная остановка, новая попытка);
- обрыв живого соединения (transport failure) — поведение не меняется,
  красный персистентен.

## Направление решения

- Источник истины — backend: `VTubeStudioService` отслеживает происхождение
  последней попытки (`manual` — команды connect/restart из панели,
  `autostart` — boot-подключение) и при manual-failure вооружает
  decay-таймер **60 секунд**.
- Истечение таймера трактуется как «пользователь ушёл»: эквивалент ручной
  остановки — `desired_running = false` + emit статуса → серый. Осознанное
  следствие: lazy reconnect по typing после затухания не вооружается.
- Таймер отменяется любой новой попыткой подключения, успехом и явным
  `disconnect()` (generation-паттерн, как `connection_generation`/`session`
  в том же сервисе).
- Frontend не меняется: тон уже управляется backend `desired_running`
  (`bcc6e28`).
- Команда `connect()` получает параметр происхождения; автостарт из
  `setup.rs` помечается `autostart` и таймер не вооружает.

## Критерии завершения

- [x] ручная ошибка → красный не дольше таймаута → серый;
- [x] ошибка автостарта → красный без таймаута;
- [x] успех / явная остановка / новая попытка сбрасывают вооружённый таймер;
- [x] transport failure живого соединения остаётся персистентно-красным;
- [x] unit-тест decay-семантики (manual вооружает, autostart нет, истечение
  сбрасывает desired и эмитит), `cargo test`, `npm test`, `npm run build`
  зелёные.

## Не входит

- изменение затухания Twitch/WebView (у Twitch своя механика — предмет
  отдельного обсуждения);
- настраиваемый пользователем таймаут (пока константа).

## Outcome

Реализовано в `2a5d56d` (2026-08-19, до squash-истории — d9c787f), ручная
проверка пользователя пройдена.

- `VTubeStudioService` различает происхождение попытки (`manual` /
  `autostart`); manual-failure вооружает decay-таймер 60 c, autostart —
  нет; новая попытка, успех и явный `disconnect()` таймер сбрасывают.
- Истечение = «пользователь ушёл»: `desired_running = false` + emit →
  серый; lazy reconnect по typing таймер не вооружает.
- Transport failure живого соединения остаётся персистентно-красным;
  frontend не менялся (тон управляется `desired_running`, `bcc6e28`).
- Unit-тесты decay-семантики в составе suite.
