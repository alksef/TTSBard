# ROADMAP-086 — Управляемая видимость провайдеров в панели TTS

## Проблема

Панель TTS безусловно показывает карточки Silero, OpenAI, Fish Audio и
локального HTTP-сервера, а каждую найденную Piper-модель добавляет ещё одной
карточкой. Экспериментальные и редко используемые варианты занимают место, а
Piper-модели появляются без явного действия пользователя. При добавлении новых
облачных провайдеров и локальных движков этот список будет только расти.

## Цель

Оставить в основной части панели только выбранные пользователем провайдеры и
добавить в правый верхний угол компактное меню с кнопкой `⋯`. В меню пользователь
управляет тем, какие провайдеры и локальные модели отображаются.

Меню видимости становится единым UX для существующих и будущих провайдеров:
добавление нового провайдера не должно автоматически загромождать панель.

## Пользовательский сценарий

1. Над списком карточек справа находится круглая icon-only кнопка `⋯` с
   `title` и `aria-label` «Настроить видимость провайдеров». Отдельный заголовок
   «Синтез речи» не добавляется: панель сохраняет структуру соседних разделов.
2. Кнопка открывает компактный popover со списком доступных провайдеров и
   checkbox для каждого из них. Отдельный заголовок «Показывать провайдеры» и
   поясняющий footer внутри popover не нужны.
3. Изменение checkbox сразу показывает или скрывает соответствующую карточку
   встроенного провайдера либо строку Piper-модели и сохраняется без отдельной
   кнопки «Сохранить».
4. Меню закрывается повторным нажатием, кликом вне него и клавишей `Escape`;
   управление доступно с клавиатуры, а фокус после закрытия возвращается на
   кнопку `⋯`.
5. Если видимых дополнительных провайдеров нет, панель остаётся полноценной и
   не показывает пустой placeholder: основной Silero остаётся доступен.

## Модель видимости

- Видимость является только настройкой представления. Она не меняет API-ключи,
  подключение, runtime-состояние, выбранный голос или конфигурацию провайдера.
- Активный TTS-провайдер всегда виден. Его checkbox нельзя выключить, пока он
  активен; рядом достаточно короткой пометки «активный».
- Silero является базовым видимым провайдером по умолчанию.
- OpenAI, Fish Audio и локальный HTTP-сервер по умолчанию скрыты, если ещё не
  настроены и не выбраны.
- Настроенный или активный встроенный провайдер при первом обновлении со старой
  версии остаётся видимым, чтобы миграция не прятала рабочую конфигурацию.
- Каждая Piper-модель использует собственный стабильный provider ID и имеет
  отдельный checkbox. Новая обнаруженная модель по умолчанию видна в меню, но
  не добавляет строку в основной блок Piper без выбора пользователя.
- Исчезнувший динамический provider ID можно удалить из сохранённого списка при
  нормализации настроек; его отсутствие не должно ломать открытие панели.
- Будущий провайдер следует тому же контракту: зарегистрирован в доступном
  списке, появляется в меню и отображается только после явного выбора либо
  когда восстановлен как активный.

Сохраняется набор стабильных provider ID, а не позиции карточек и не
отображаемые названия. Для встроенных провайдеров используются существующие ID
`silero`, `openai`, `fish`, `local-http`; для Piper — текущие
`local-piper:<model>`.

## Представление списка

На первом этапе меню разделяет варианты тремя небольшими группами:

- «Облачные и интеграции»: Silero, OpenAI, Fish Audio;
- «Локальный сервер»: локальный HTTP-провайдер;
- «Piper»: обнаруженные модели как визуально вложенные подпункты с собственными
  checkbox.

Группировка служит только представлению. Source of truth остаётся единым списком
доступных провайдеров с ID и metadata, чтобы следующий облачный или локальный
движок не требовал отдельной логики сохранения видимости.

## Блок Piper в основной панели

Видимые Piper-модели не оформляются отдельными полноразмерными provider cards.
Они объединяются в один блок:

- заголовок `Piper` с подписью `Локальные модели` один раз объясняет тип и
  происхождение всех моделей;
- каждая модель является компактной строкой с radio-кнопкой выбора, своим
  `display_name` и trailing runtime-статусом;
- блок не отображается, если пользователь скрыл все Piper-модели;
- появление модели в списке уже означает, что она обнаружена, поэтому текст
  «Модель обнаружена» не выводится;
- для ненагруженной модели trailing-область остаётся пустой;
- во время подготовки отображаются spinner и `Загрузка…`;
- после успешной подготовки отображаются зелёная точка и `Загружена`;
- при ошибке отображается красная компактная метка `Ошибка загрузки`, а полная
  диагностическая причина остаётся доступной без постоянного увеличения высоты
  всех строк.

Активная строка выделяется тем же selected-состоянием, что и встроенные
провайдеры. Runtime-статус и активность не объединяются: модель может оставаться
загруженной в кеше после переключения на другой провайдер.

## Границы реализации

1. Ввести persist-контракт набора видимых provider ID с безопасной миграцией
   старых `settings.json`.
2. Получать пункты меню из общего списка встроенных и runtime-провайдеров, не
   дублируя отдельный список названий только для popover.
3. Отделить вычисление доступности, видимости и активного состояния провайдера;
   покрыть это чистыми frontend-тестами.
4. Добавить компактную строку управления с кнопкой `⋯`, доступный popover и
   условный рендеринг карточек без нового заголовка панели.
5. Заменить отдельные Piper provider cards общим блоком компактных строк и
   перенести runtime-статус в trailing-область каждой строки.
6. Проверить реактивное появление/исчезновение Piper-моделей, сохранение между
   перезапусками и миграцию существующих настроек.

Конкретную продуктовую реализацию выполнить через task → DeepSeek → независимое
review согласно `docs/development/ai-workflow.md`.

## Не входит

- установка, импорт, скачивание или удаление локальных моделей;
- включение и отключение runtime провайдера;
- изменение выбора активного провайдера из самого меню видимости;
- рефакторинг backend TTS registry, не требуемый persist-контрактом;
- добавление нового TTS-провайдера.

## Критерии готовности

- OpenAI, Fish Audio, локальный HTTP-сервер и каждая Piper-модель могут быть
  независимо показаны или скрыты через меню `⋯`.
- Скрытие карточки не меняет настройки и runtime-состояние провайдера.
- Активный провайдер нельзя скрыть; он не исчезает из панели при загрузке или
  обновлении настроек.
- Выбор видимости сохраняется после перезапуска приложения.
- Старые настройки без нового поля читаются; Silero и ранее настроенный либо
  активный провайдер остаются видимыми.
- Новая Piper-модель не появляется строкой сама, но доступна для включения в
  меню.
- Удалённая Piper-модель не оставляет сломанную строку или ошибку открытия
  меню.
- Все видимые Piper-модели находятся в одном блоке `Piper / Локальные модели`;
  повторяющиеся подписи у каждой модели отсутствуют.
- Ненагруженная модель не показывает статус «обнаружена»; состояния загрузки,
  готовности и ошибки отображаются компактно рядом с соответствующей моделью.
- Popover корректно работает мышью и клавиатурой, на узкой ширине, в светлой и
  тёмной темах, без горизонтального overflow.
- Frontend tests, Rust settings tests, `npm run build` и проверка документации
  проходят; Rust-команды на Windows запускаются только через
  `scripts/cargo.ps1`.

## Outcome

Панель TTS получила сохраняемое управление видимостью provider ID через
круглую кнопку `⋯`. Меню разделяет облачные и интеграционные провайдеры,
локальный HTTP-сервер и вложенный список Piper-моделей. Активный провайдер
виден принудительно и не может быть скрыт.

Piper-модели больше не рендерятся отдельными крупными карточками: видимые
модели находятся в одном блоке `Piper / Локальные модели`. Статус
«Модель обнаружена» удалён; рядом с моделью показываются только загрузка,
готовность или ошибка. Новая обнаруженная Piper-модель доступна в меню, но не
загромождает основную панель автоматически.

Настройка совместима со старыми `settings.json`; сохранение visibility не
меняет выбор, конфигурацию или runtime TTS-провайдера. Пользователь подтвердил
ручную проверку 2026-08-28.

1. Persist и migration: поле видимых provider ID в TTS settings, DTO и точечные

2. Frontend model: единый derived-список пунктов меню и чистая логика
   нормализации доступных, активных и видимых ID.
3. UI: компактная кнопка панели, доступный popover, общий Piper-блок,

4. Независимая ручная проверка миграции, Piper discovery и сохранения после
   перезапуска.
