# ROADMAP-101 — Маршрутизация входящих и единая вкладка редактирования

## Цель

Дать пользователю явный контроль над доставкой текста из Input Server и OCR:
входящая реплика либо ожидает подтверждения, либо обрабатывается автоматически,
а после принятия отправляется в выбранные аудио, WebView и Twitch назначения.
Редактирование входящего текста использует одну переиспользуемую вкладку и не
создаёт новый черновик при каждом вызове.

## Согласованное направление

2026-09-09 согласованы общая маршрутизация входящих и единая служебная вкладка
`Входящий текст`.

- Общая source-neutral настройка входящих применяется одинаково к Input Server
  и OCR; отдельные маршруты по producer в первый релиз не входят.
- Текущая галка переименовывается из узкого «Автовоспроизведение» в
  «Принимать автоматически»: она определяет, проходит ли текст через ручное
  подтверждение, но не определяет маршрут доставки.
- Рядом с галкой располагается селектор маршрута с теми же визуальными
  принципами, иконками назначений, tooltip и keyboard/focus-поведением, что у
  селектора маршрута редактора.
- Набор маршрутов входящих является отдельным typed-контрактом и не кодируется
  префиксами пользовательского текста.
- Кнопка `Редактировать` открывает или активирует одну вкладку `Входящий текст` и
  заменяет её содержимое выбранной входящей репликой.

## Маршруты входящих

Первый релиз предоставляет четыре допустимые комбинации:

| Маршрут | Аудио | WebView | Twitch |
|---|:---:|:---:|:---:|
| Только аудио | ✓ |  |  |
| Аудио + Web | ✓ | ✓ |  |
| Аудио + Twitch | ✓ |  | ✓ |
| Везде | ✓ | ✓ | ✓ |

Аудио обязательно для всех маршрутов входящих. Комбинации WebView-only,
Twitch-only и пустой маршрут не входят: входящий поток остаётся TTS-сценарием,
а интеграции являются дополнительными получателями результата.

Маршрут хранится как явная persisted-настройка общей incoming policy. Backend
передаёт его в snapshot speech job как transport policy; ведущие `!`, `!!` и
`!t` не добавляются к внешнему тексту и не используются как внутренний контракт.
Это сохраняет исходный текст и позволяет выразить новый маршрут
`Аудио + Twitch`, которого нет среди текущих editor-префиксов.

## Пользовательское поведение

### Автоматическая обработка включена

1. Input Server или OCR передаёт текст в общий incoming seam.
2. После валидации сразу создаётся speech job с выбранным маршрутом.
3. Аудио проходит существующий TTS/playback pipeline; после готовности результат
   также доставляется в разрешённые WebView и Twitch назначения.
4. Задача отображается в существующем списке входящей активности и общей очереди;
   отдельная очередь доставки не создаётся.

### Автоматическая обработка выключена

1. Текст остаётся в `IncomingTextInbox` до действия пользователя.
2. `Принять` создаёт speech job с маршрутом, выбранным на момент принятия.
3. `Редактировать` изымает элемент из inbox, переносит его в служебную вкладку и
   назначает этой вкладке текущий маршрут входящих.
4. `Отклонить` удаляет элемент без синтеза и доставки.

Селектор доступен в обоих режимах. Его изменение влияет на будущие автоматические
поступления и ручные принятия, но не меняет snapshot уже созданных speech jobs.

## Вкладка `Входящий текст`

- Вкладка является обычной редактируемой вкладкой с устойчивым служебным
  назначением, но создаётся только при первом нажатии `Редактировать`.
- Повторное редактирование находит её по стабильному признаку, активирует и
  полностью заменяет текст новой входящей репликой; новая вкладка не создаётся.
- Incoming route применяется к автоматической обработке и действию `Принять`.
  После перехода в режим редактирования доставкой управляет обычный селектор
  редактора: существующий маршрут переиспользуемой вкладки сохраняется, а новая
  вкладка использует editor default. Маршрут `Аудио + Twitch` не подменяется
  ближайшим editor route.
- Пользователь может закрыть вкладку. Следующее редактирование создаёт новую
  вкладку с тем же служебным назначением и названием.
- Переименование вкладки пользователем не должно лишать её служебной идентичности
  и приводить к созданию дубликата.
- Замена выполняется намеренно без дополнительного диалога: вкладка служит одним
  входящим edit-buffer, а не хранилищем нескольких черновиков.

## Охват реализации

Направление затрагивает единый incoming settings/runtime contract, persistence и
миграцию, создание job snapshot, ручное принятие, frontend composable входящих,
toolbar вкладки `Входящие`, модель вкладок редактора, локализацию и contract/UI
тесты. Реализацию следует разбить минимум на два task-scoped изменения:

1. Backend: typed incoming route, persistence/migration и сквозная доставка для
   автоматического и ручного путей.
2. Frontend: селектор по образцу редактора и переиспользуемая вкладка
   `Входящий текст`.

Backend-контракт должен появиться раньше либо вместе с минимальным frontend
срезом: UI не должен сохранять маршрут, который фактически игнорируется.

## Миграция и совместимость

- У существующих настроек без маршрута применяется `Только аудио`, чтобы
  обновление не начало неожиданно публиковать прежние входящие в WebView или
  Twitch.
- Существующее значение автоматической обработки сохраняется без изменения.
- HTTP API приёма текста не получает обязательных новых параметров; маршрут
  остаётся политикой приложения.
- Pending items не обязаны хранить копию маршрута: ручное принятие использует
  актуальный выбор. Уже созданные speech jobs сохраняют immutable snapshot.

## Ошибки и состояния

- Недоступность WebView или Twitch не должна отменять уже выполненную локальную
  озвучку; результат доставки отражает успех и ошибку каждого выбранного
  назначения по существующему контракту delivery outcomes.
- Недоступное назначение остаётся видимым в селекторе и сопровождается понятным
  состоянием/подсказкой по аналогии с редактором; сохранённый маршрут не должен
  молча сбрасываться.
- Ошибка сохранения настройки возвращает предыдущий выбор в UI и показывает
  локализованное сообщение.
- Двойное подтверждение одного pending item не создаёт две speech jobs.
- Во время замены вкладки stale async result не должен перезаписать более поздний
  выбранный входящий текст.

## Критерии готовности

- Галка `Принимать автоматически` и incoming route сохраняются и синхронно
  отражаются во всех UI, использующих общую incoming policy.
- Input Server и OCR проходят один и тот же маршрут во всех четырёх комбинациях,
  как при автоматической обработке, так и после ручного принятия.
- Исходный внешний текст не изменяется route-префиксами.
- Обновление со старых настроек сохраняет auto-process и выбирает
  `Только аудио`.
- Селектор входящих визуально и по доступности следует эталонному editor route
  selector, корректен в узкой ширине и обеих темах, не создаёт горизонтальный
  overflow.
- Повторное `Редактировать` заменяет текст и маршрут ровно одной вкладки
  `Входящий текст`; закрытие вкладки позволяет создать её заново, переименование
  не создаёт дубликатов.
- Проверены success, cancel/error/retry и stale-result сценарии; пройдены
  frontend-тесты, `npm run build`, целевые Rust-тесты через `scripts/cargo.ps1`
  и ручная runtime-проверка Input Server/OCR × auto/manual × четыре маршрута.

## Outcome

Входящие Input Server и OCR получили сохраняемый селектор из четырёх маршрутов:
`Только аудио`, `Аудио + WebView`, `Аудио + Twitch` и `Везде`. Выбранный маршрут
используется при автоматическом и ручном принятии, а старые настройки безопасно
мигрируют на `Только аудио`.

Галка переименована в `Принимать автоматически`, а селектор расположен сразу
после неё. Действие `Редактировать` переиспользует одну служебную вкладку
`Входящий текст`, не создавая новые вкладки при каждом вызове. Маршрут после
перехода в редактор остаётся под контролем самой вкладки редактора.

Добавлены backend- и frontend-тесты сериализации, миграции, маршрутизации,
конкурирующих сохранений и переиспользования вкладки. Прошли 1115 frontend-
тестов, production build, целевые Rust-тесты Input Server и вкладок, Rust check,
проверка документации и `git diff --check`. Отдельный ручной smoke с реально
подключёнными WebView, Twitch и OCR в этой сессии не выполнялся.

## Не входит

- отдельный маршрут для каждого producer;
- выбор маршрута в каждом отдельном pending item;
- WebView-only, Twitch-only и произвольный пустой набор назначений;
- изменение внешнего HTTP API ради передачи маршрута каждым запросом;
- несколько параллельных служебных вкладок для входящих;
- сохранение истории содержимого вкладки `Входящий текст`.
