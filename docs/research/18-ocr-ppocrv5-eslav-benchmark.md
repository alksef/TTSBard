## Вопрос

Подтверждает ли небольшой корпус реальных игровых RU/EN-кадров выбор
PP-OCRv5 mobile + eSlav recognition как default-модели, и каковы фактические
качество и CPU-латентность на зафиксированном конфиге?

## Метод

- Runtime: тот же конфиг, что закоммичен в `src-tauri/src/ocr/runtime.rs`
  (CPU, 2/1 потока, без cls, det limit `Min 736`, rec `[3,48,320]` batch 6),
  исполнение — release `rapidocr-cli` апстримного rapidocr-rs (совместимость
  подтверждена ранее).
- Корпус v001 (gitignored `.work/ai/2026-09-01-ocr-corpus-benchmark/`):
  - 2 RU-кадра визуальной новеллы с диалогами (предоставлены пользователем,
    уже обрезаны до диалоговой полосы ~950×255);
  - 1 EN-кадр со стилизованным логотипом (Steam Store);
  - 3 кадра десктопного UI из runtime-пробы (compatibility smoke, см.
    исследование 16) —_latency-контекст, не игровой.
- Ground truth: дословная расшифровка в порядке чтения (AI vision, неуверенная
пунктуация сглаживается loose-CER: без регистра и пунктуации).
- Метрики: CER/WER по конкатенации строк в порядке чтения; латентность —
  среднее из 3 прогонов на кадр, холодная загрузка моделей ~160 мс вне метрики.

Ключевое наблюдение по ru-01: сама реплика распознана безошибочно

прочитаны как `X`/`B`, мелкий индикатор «1.5» пропущен, декоративный глиф
перед именем спикера → `*`.

## Выводы

1. **Крупный диалоговый текст (основной сценарий one-shot OCR → TTS)
   распознаётся практически безошибочно.** Выбор eSlav PP-OCRv5 mobile
   подтверждён для RU/EN default-модели.
2. **Мелкий плотный текст фрагментируется детектором по словам** (25 боксов на
   реплику). Порядок чтения сохраняется, конкатенация остаётся читаемой, но:
   - теряются пробелы на стыках («уверена.Я»);
   - растут гомоглифные замены латиница↔кириллица (`Koкopo`, `вKуCнO.`,
     `A-a-am.`) — для TTS это опаснее, чем для чтения: смешанный алфавит
     озвучивается абракадаброй.
3. **Латентность 0.6–0.76 с на диалоговую полосу на CPU** — приемлемо для
   one-shot сценария. Детект доминирует (~0.4 с): узкая полоса 950×255
   апскейлится до min-side 736 → ~2690×736. Для широких полос альтернатива
   `LimitType::Max` потенциально дешевле, но рискует пропустить мелкий текст —
   проверяется настройкой в P2/P3, не меняет выбор модели.
4. Артефакты вокруг полезного текста (иконки → `X`/`B`, вотермарки) —
   ожидаемое поведение one-shot захвата «как есть»; фильтрация не входит в MVP.

## Решение

P0 ROADMAP-088 закрыт: модель подтверждена, preprocessing/postprocessing и
`manifest.json` зафиксированы (закоммичены в `src-tauri/src/ocr/`), качество и
латентность измерены. Корпус минимальный (2 игровых RU-кадра + 1 EN); при
расширении — v002 в той же рабочей области, либо ручной сценарий P4.

Точки настройки, переданные в P2/P3: поведение det limit на широких полосах,
порог отсечения мусорных боксов (иконки), сохранение пробелов при
word-фрагментации.
