# RUAccent: benchmark, переносимость в Rust и поиск существующих порт-ов

Продолжение `.work/silero-stress-research.md` (2026-08-21). Все измерения и
артефакты: `E:\TTS\ruaccent-bench\` (`RESULTS.md`, `PORT-ANALYSIS.md`,
`bench.py`, `bench_silero.py`, `per_text.py`, `*.json`, `*.log`).

## Benchmark (2026-08-22, этот ПК, CPU)

Набор: 11 предложений с омографами (оба варианта каждой пары: замок, плачу,
белки, мука, коса, уже) + 2 предложения с двумя омографами сразу
(«Замок был на холме под замком.», «А мука в телеге вызывала муку.»).
Warm, 50×13 прогонов; silero — PyTorch CPU 1 thread.

| Модель | Cold load | mean/предл. | p50 | p95 | Простые | Двойные |
| --- | ---: | ---: | ---: | ---: | --- | --- |
| **silero v1.4** (PyTorch, 51 MiB) | **0.42 s** | **3.1 ms** | 3.2 ms | 4.7 ms | 9/11 | 0/2 |
| **ruaccent tiny** (ONNX, ~165 MiB pack) | 6.0 s | 11.1 ms | 7.6 ms | 31 ms | **11/11** | 0/2 |
| ruaccent tiny2.1 | 6.1 s | 12.0 ms | 8.0 ms | 35 ms | 8/11 | 0/2 |
| ruaccent turbo3.1 | 7.6 s | 50.0 ms | 54 ms | 87 ms | 9/11 | 0/2 |

Выводы по скорости: для встраивания скорость достаточна у всех — доли секунды
на целый абзац. Различия: silero быстрее и грузится мгновенно, но это
PyTorch/TorchScript; tiny — ONNX, лучший скор на наборе; turbo3.1 в ~5 раз
медленнее без выигрыша в качестве.

Критичная находка по качеству: **все модели (включая silero) проваливают
предложения, где одна лемма встречается в двух разных значениях**
(«под замком» — все дали «крепость»; «мука…муку» — все одним значением).
Разрешение, по-видимому, идёт по лемме без учёта контекста повторов. Прямое
подтверждение приоритета «явный выбор пользователя > override > модель»
и необходимости слоя override-ов в ROADMAP-081.

## Переносимость обёртки в Rust без sidecar

Полный разбор кода: `E:\TTS\ruaccent-bench\PORT-ANALYSIS.md`. Итог:

- Python-обёртка ~1450 строк; нет ни torch, ни динамического кода —
  только ONNX + токенизаторы + JSON-словари + regex. **Порт целиком возможен**.
- `transformers.AutoTokenizer` не блокер: официальный Rust-crate `tokenizers`
  — тот же движок, что под капотом Python, ест `tokenizer.json` из pack'а.
  Вручную переносится только CharTokenizer (106 строк) и обвязка вызовов.
- **RuleEngine + koziev (410 строк, 189 MB данных) — мёртвый код** в основном
  пайплайне (`process_all`): загружается, но не вызывается. В порте не нужен.
- В `tiny_mode` stress_usage_predictor (115 MB) не вызывается — опционален.

Риски порта — parity токенизаторов (NLI pair-encoding для омографов) и parity
razdel-сплиттера. Метод: golden-тесты (вход → токены → ONNX outputs → строка)
со снятым Python-эталоном, портировать по слоям со сверкой.

## Поиск существующих Rust-порт-ов (2026-08-22)

GitHub (репо + language:rust), crates.io, веб-поиск — **актуального Rust-порта
ruaccent/silero-stress не существует**:

- crate `amdm` (2026-01) — клиент amdm.ru (песни), не порт; упоминаемый в
  ресёрче Rust-порт старой версии дал 3/6 — заброшен;
- `silero-vad-rust` — порт Silero VAD, не accentor;
- `floravox-g2p` (2026-08, Rust) — espeak-ng replacement для Piper-подобных
  движков, лексиконы англ., русского ударения не решает (отдельно интересен
  для Piper-пути ROADMAP-081);
- вокруг ruaccent живое только Python: stressonnx (не решает омографы),
  ruphon (Python фонемизер, см. отдельную заметку), HTTP-microservice sidecar-ы.

## Итог

**Есть смысл делать собственный нативный Rust-порт RUAccent `tiny`** (этап 2
ROADMAP-081): ниша пустая, все блоки готовые (`ort`, `tokenizers`, `flate2`),
~1–2 недели с golden-сверкой по Python-эталону. Первым кандидатом остаётся
`tiny` (лучший скор + ONNX + 165 MiB); silero — быстрее, но требует R&D по
HomoSolver (BERT-граф, не ONNX). Перед release — расширенный regression-набор
(скор на 13 предложениях не доказательство качества) и фиксация лицензий
моделей (PyPI метаданные Apache vs MIT в README).
