# AI-assisted development workflow

Этот документ описывает опциональный процесс делегирования реализации DeepSeek
Flash через OpenCode. Он применяется по выбору пользователя и не является
обязательным процессом проекта. Перед первым применением в новой сессии ведущий
агент уточняет выбор, если пользователь ещё не задал его, и сохраняет выбранный
режим до новых указаний. Без делегирования ведущий агент реализует изменения сам.
Задания, промежуточные ревью и логи являются локальными рабочими материалами и
не коммитятся в репозиторий.

## Роли

- Codex/Claude исследует код, ограничивает scope, ставит задачу и независимо
  проверяет результат.
- DeepSeek пишет implementation code по конкретному task-файлу.
- Пользователь утверждает значимые архитектурные решения и коммиты.

Мелкие правки документации, конфигурации, опечаток и локальных build errors
ведущий агент может выполнять напрямую. При выбранном делегировании используется
цикл task → DeepSeek → review.

Защитное исключение для самостоятельного завершения ведущим агентом описано
в разделе [«Лимит попыток»](#лимит-попыток).

## Постоянные и временные материалы

В Git хранятся только материалы, полезные после завершения конкретной сессии:

- направление продукта — `docs/roadmap/`;
- принятое решение и его причины — `docs/decisions/`;
- отобранное исследование — `docs/research/`;
- самостоятельная долгосрочная implementation task — `docs/tasks/`.

В `.work/ai/<work-id>/` хранятся prompts, corrective tasks, ревью, вывод команд
и скриншоты. Локальная задача DeepSeek не становится постоянной документацией
автоматически.

Полные (repo-wide) ревью кода и release-review'ы не привязаны к одной задаче и
оформляются отдельными подкаталогами `.work/ai/full-review/<id>/` с baseline
и результатами проверки.
Task-scoped ревью текущей задачи остаются в `.work/ai/<work-id>/reviews/` и не
смешиваются с full-review-областями.

### Выбор постоянного документа

По умолчанию конкретная реализация начинается и заканчивается локальным task в
`.work/ai/`. Документ добавляется в Git только при наличии результата, который
должен пережить отдельную AI-сессию:

- `docs/roadmap/` — направление изменяет пользовательскую ценность или проходит
  несколько этапов и требует явного lifecycle-статуса;
- `docs/tasks/` — ограниченная реализация должна быть самостоятельно исполнима
  позже, содержит устойчивые ограничения, scope, критерии и проверки;
- `docs/decisions/` — выбран один из значимых вариантов и важны причины,
  последствия либо условия пересмотра;
- `docs/research/` — сравнение опирается на проверяемые источники, имеет вывод и
  связано со следующим roadmap item или decision.

План декомпозиции, prompt одного запуска, corrective iteration и отчёт о
выполненных командах остаются в `.work/ai/`. Один результат не оформляется сразу
в нескольких постоянных документах без разных долговечных назначений: например,
roadmap хранит направление, а decision — только выбранный архитектурный вариант.

## Создание рабочей области

Из корня репозитория:

```powershell
$workId = "YYYY-MM-DD-short-name"
$work = ".work/ai/$workId"
New-Item -ItemType Directory -Force $work | Out-Null
git rev-parse HEAD | Set-Content "$work/baseline-sha.txt"
git status --short | Set-Content "$work/baseline-status.txt"
```

Для реализации сохраняются baseline, task с ограничениями и результаты проверки.
Baseline нужен, чтобы не принять существующие пользовательские изменения за
результат агента. Отдельный `context.md` и каталоги `tasks/`, `reviews/`, `logs/`,
`screenshots/` создаются по необходимости; повторять контекст task-файла не нужно.

## Размер задачи

Одна задача — один проверяемый результат с ограниченным scope и собственными
критериями приёмки. Связанные изменения в нескольких файлах или слоях допустимы.
Независимые изменения и несвязанный cleanup выносятся отдельно. Широкий roadmap
item сначала разбивается на такие задачи; дробление по одному файлу или модулю
само по себе не требуется.

## Выбор модели

Для всех задач DeepSeek используется только `deepseek/deepseek-flash`.
Сложные изменения сначала декомпозируются в локальной рабочей области на узкие
задачи с отдельными критериями приёмки. Для небольшой задачи отдельный план
не нужен.

## Task-файл

`tasks/001.md` должен содержать:

1. цель и наблюдаемое ожидаемое поведение;
2. исходный контекст и ограничения;
3. разрешённые и запрещённые пути;
4. существующий source of truth или похожую реализацию;
5. edge cases и regression risks;
6. точные команды проверки;
7. критерии готовности без требования самостоятельно коммитить изменения.

В начале task-файла явно указывается роль: исполнитель DeepSeek реализует
задание в разрешённых путях, не делегирует его дальше и не создаёт коммиты.
Роль ведущего агента из `AGENTS.md` не переносится на исполнителя.

Для UI указываются конкретный эталонный компонент/CSS-класс, состояния success,
cancel, error, retry и stale async result, узкая ширина, обе темы и отсутствие
горизонтального overflow. Icon-only controls требуют `title` и `aria-label`.

### Формат постановки

План кратко описывает шаги и ожидаемые результаты. Задание DeepSeek содержит
необходимый контекст: что изменить, где искать, какие ограничения соблюдать и
как проверить результат. Готовый код и пошаговый рецепт реализации не включаются.
Точные технические детали указываются только там, где они необходимы для
совместимости или соблюдения требований. Константы, строки и таблицы данных
можно приводить явно.

Значимые архитектурные решения согласуются с пользователем. Локальные детали
реализации DeepSeek выбирает в рамках задачи и существующих контрактов.

Задание не должно ссылаться на недоступную исполнителю память прошлых сессий.
Нужный контекст и пути к локальным материалам включаются в сам task-файл.

## Запуск OpenCode в PowerShell

```powershell
$repo = (Get-Location).Path
$task = ".work/ai/$workId/tasks/001.md"
$log = ".work/ai/$workId/logs/001-opencode.log"
New-Item -ItemType Directory -Force (Split-Path $log) | Out-Null
$prompt = Get-Content -LiteralPath $task -Raw

& opencode run `
  --model deepseek/deepseek-flash `
  --dir $repo `
  --log-level ERROR `
  $prompt 2>&1 | Tee-Object -FilePath $log
$openCodeExit = $LASTEXITCODE
```

Путь к checkout не фиксируется в документации. Перед продолжением проверяется
`$openCodeExit`, а не только текст ответа модели.

Перед первым запуском в текущем окружении проверьте `opencode --version` и
`opencode models deepseek`: в списке должен присутствовать
`deepseek/deepseek-flash`. Модель всегда передаётся явно через `--model`,
независимо от глобальных настроек OpenCode. Наличие модели в каталоге ещё не
подтверждает исправность авторизации или успешный ответ API.

Разрешённые пути в prompt задают scope, но не обеспечивают техническую изоляцию.
Не запускайте одновременно исполнителей с пересекающимися путями в одном
checkout. Перед review убедитесь, что процесс OpenCode завершился и больше не
меняет файлы.

Timeout выбирается с учётом объёма задачи. Длительный запуск контролируется по
обновлению лога и состоянию процесса. Истечение timeout не подтверждает
завершение процесса. Перед повторным запуском или самостоятельными исправлениями
ведущий агент проверяет фактический diff и завершает оставшийся процесс
предыдущей попытки.

## Независимая проверка

После каждого запуска ведущий агент:

1. сравнивает `git status --short` с baseline;
2. проверяет diff только разрешённых task paths;
3. читает изменённый код и трассирует end-to-end поведение;
4. запускает проверки, соответствующие риску;
5. записывает verdict в `.work/ai/<work-id>/reviews/`;
6. при неудаче действует по [лимиту попыток](#лимит-попыток).

Минимальная матрица проверок:

| Изменение | Проверка |
|---|---|
| TypeScript/Vue | `npm test` при затронутых тестах, затем `npm run build` |
| Rust | целевые тесты и check через `scripts/cargo.ps1` с нужными аргументами `cargo` |
| UI/runtime | релевантный ручной сценарий и состояния error/cancel/retry |
| Packaging/native deps | `scripts/build.ps1 -Mode debug`, при необходимости release |

На Windows task-файлы и независимая проверка не должны вызывать bare `cargo`:
`scripts/cargo.ps1` подготавливает окружение для Rust-команд, а полная сборка
выполняется только через `scripts/build.ps1`, учитывающий локальную конфигурацию.

Review проводится по постоянному
[шаблону code review](./templates/code-review.md). Он задаёт базовый профиль
рисков, формат findings и структуру verdict. Критерии конкретной задачи имеют
приоритет и дополняют шаблон; сам шаблон не заменяет чтение diff, трассировку
поведения и фактические проверки.

Чекбоксы и финальный ответ DeepSeek не являются доказательством. Готовность
подтверждают diff, проверки и фактический сценарий.

## Лимит попыток

На задачу допускаются две попытки DeepSeek: первичная реализация и одно
исправление по результатам проверки. После первой неудачи ведущий агент создаёт
короткий corrective task с конкретными замечаниями. После второй неудачи
прекращает вызовы DeepSeek по этой задаче, самостоятельно завершает реализацию
и выполняет проверки независимо от числа замечаний. Новая сессия, task-файл
или декомпозиция той же задачи не обнуляют лимит.

## Завершение

- Перед закрытием roadmap/task сверить canonical status и индекс, удалить
  завершённую task из списка текущих задач и убедиться, что её устойчивый
  результат перенесён в owning roadmap, decision или профильную документацию.
- Обновить roadmap/decision/research только если появился долговечный результат.
- Подготовить scoped commit без чужих изменений.
- Не добавлять `.work/` в Git даже принудительно.
- После принятия результата локальную рабочую область можно удалить; если она
  нужна для продолжения, она остаётся только на машине разработчика.
