# AI-assisted development workflow — Qwen3-Coder (локальный)

Этот документ — вариация
[базового AI-workflow](./ai-workflow.md) для исполнителя Qwen3-Coder,
запускаемого локально через Ollama. Он описывает **только отличия** от
базового процесса: исполнителя, выбор режима мышления вместо модели по
сложности, фактический тег модели, параметры и команду запуска. Всё, что
здесь не оговорено явно (роли, рабочая область в `.work/ai/`, размер задачи,
task-файл, независимая проверка, завершение), действует по базовому
[ai-workflow.md](./ai-workflow.md) без изменений.

## Исполнитель и обоснование выбора

Qwen3-Coder — thinking-модель, заточенная под agentic-кодинг (постобучение с
long-horizon Agent RL и поддержкой tool calling). В отличие от линеек с
отдельными моделями «под задачу», здесь одна модель переключает режим
рассуждения маркером в запросе. Поэтому **выбор модели по сложности задачи из
базового workflow заменяется выбором режима мышления** в этом документе.

Модель крутится локально в Ollama; OpenCode подключается к ней через
OpenAI-совместимый endpoint `http://127.0.0.1:11434/v1`.

## Выбор режима мышления вместо выбора модели

Базовый workflow выбирает `deepseek-v4-flash` / `pro` / `reasoner` под размер
задачи. Для Qwen3-Coder роль этого выбора выполняют маркеры режима мышления,
которые ставятся **в первой строке task-файла** и применяются к этому запуску:

- `/no_think` — один файл или 1–2 тесно связанных файла, известный паттерн,
  локальный тест либо исправление без архитектурного выбора. Прямой ответ,
  минимальная трата токенов и времени. Соответствует `flash`.
- `/think` — несколько слоёв/файлов, новый seam/API, рефакторинг или
  нетривиальный риск регрессии; алгоритмический или research-heavy анализ, где
  сравнение подходов важнее скорости. Соответствует `pro` / `reasoner`.

Маркер действует на весь промпт и переключается пошёрново, но в рамках одной
задачи режим фиксируется в task-файле. Менять его по ходу исправлений можно
только при смене характера работы (например, `no_think` для мелкой правки после
`think`-декомпозиции).

## Модель и параметры

| Параметр | Значение | Примечание |
|---|---|---|
| Исполнитель по умолчанию | `ollama/qwen3-coder-coder:30b` | Зарегистрирован в `opencode.json` |
| Базовая модель | `qwen3-coder:30b` (Q4_K_M, 30.5B) | Локальный GGUF в Ollama |
| `temperature` | `0.2` | Понижена относительно диалогового дефолта `0.7` для стабильности имён, сигнатур и путей при генерации кода |
| `top_p` / `top_k` | `0.8` / `20` | Дефолты Qwen |
| `repeat_penalty` | `1.05` | Дефолт Qwen |
| Контекст | `131072` | Достаточно для task-файла с контекстом кода |

`temperature` понижена осознанно: дефолт `0.7` рассчитан на диалог, где
живость рассуждения важнее детерминизма. Для кода низкая температура снижает
частоту галлюцинаций имён функций, сигнатур и путей — основной класс ошибок
локального исполнителя, который всё равно ловит независимая проверка, но
дешевле предотвратить, чем исправлять corrective-итерацией.

Тег `qwen3-coder-coder:30b` построен как Ollama-вариант поверх `qwen3-coder:30b`
с уже применёнными параметрами, чтобы каждый запуск через OpenCode получал
правильную температуру без явного override в вызове. Пересоздать вариант можно
через `ollama create` из `Modelfile`, ссылающегося `FROM qwen3-coder:30b` и
`PARAMETER temperature 0.2`.

Альтернативный тег `qwen3-coder:64k` (контекст 65536) зарегистрирован в
`opencode.json` для коротких задач, где важнее скорость, чем запас контекста;
по умолчанию используется `:30b`.

## Task-файл

Структура task-файла соответствует базовому workflow. Единственное дополнение —
**режим мышления задаётся первой строкой** task-файла:

```markdown
/no_think

# Цель
…

# Разрешённые пути
…
```

либо `/think` для задач, требующих рассуждения. Остальные разделы (цель,
контекст, ограничения, source of truth, edge cases, команды проверки, критерии
готовности) — по [базовому ai-workflow](./ai-workflow.md).

Qwen3-Coder устойчиво следует явным ограничениям: чётко перечисленные
разрешённые и запрещённые пути, явный source of truth и конкретные команды
проверки снижают дрейф. Формулировка «не коммить изменения, только редактируй
перечисленные файлы» соблюдается надёжнее, когда она вынесена в отдельный
короткий блок в начале task-файла, а не растворена в прозе.

## Запуск OpenCode в PowerShell

```powershell
$repo = (Get-Location).Path
$task = ".work/ai/$workId/tasks/001.md"
$log = ".work/ai/$workId/logs/001-opencode.log"
$prompt = Get-Content -LiteralPath $task -Raw

& opencode run `
  --model ollama/qwen3-coder-coder:30b `
  --dir $repo `
  --log-level ERROR `
  $prompt 2>&1 | Tee-Object -FilePath $log
$openCodeExit = $LASTEXITCODE
```

Отличия от базовой команды — только флаг `--model`: вместо
`deepseek/deepseek-v4-pro` используется `ollama/qwen3-coder-coder:30b`. Параметр
`--dir` и проверка `$LASTEXITCODE` вместо текста ответа — без изменений.

Запуск `opencode` может выводить безобидную ошибку
`Unable to connect … models.dev` при старте: это попытка подтянуть внешний
каталог моделей, который недоступен офлайн. На работу локального провайдера
Ollama она не влияет и не является признаком сбоя задачи.

### Локальность и скорость

Локальная модель отвечает медленнее облачной, и время сильно зависит от
аппаратуры и длины контекста. Внешний timeout оболочки задаётся с запасом;
истечение timeout **не считается** завершением — по базовому правилу ведущий
агент сначала проверяет оставшийся процесс `opencode`/`ollama` и фактический
diff и только при отсутствии прогресса останавливает запуск как зависший.

После каждого запуска проверяется, что процесс не остался в фоне: зависший
`opencode` продолжит редактировать файлы после формального завершения сессии.

## Независимая проверка

Полностью по [базовому ai-workflow](./ai-workflow.md): сравнение с baseline,
task-scoped diff, трассировка поведения, проверки по риску, verdict в
`.work/ai/<work-id>/reviews/`. Чек-лист и финальный ответ модели
**не являются доказательством** — особенно thinking-блок, который может
содержать правдоподобное, но неверное рассуждение. Готовность подтверждают
только diff, проверки и фактический сценарий.

Один нюанс локального исполнителя: Rust-сборка недоступна внутри `opencode`
(нет `libclang`), поэтому `cargo` всегда запускает ведущий агент (Claude) через
`scripts/cargo.ps1`, а полная сборка — через `scripts/build.ps1`. Исполнителю в
task-файле достаточно команд `cargo`-проверок как **критериев**, а не действий,
которые он должен выполнить сам.
