# Шаблон code review

Этот шаблон используется для независимой проверки реализации после запуска
DeepSeek. Review сохраняется локально как
`.work/ai/<work-id>/reviews/review-NNN-YYYY-MM-DD.md`, где `NNN` — номер итерации
с ведущими нулями. Сам локальный отчёт не коммитится.

Проверяющий применяет только релевантные изменению пункты, но явно учитывает
критерии task-файла, task-scoped diff и фактические результаты проверок.

## Профиль рисков

### Rust

- обработка ошибок без необоснованных `unwrap()`/`expect()` и без потери
  полезного контекста;
- владение, лишние clone/allocation и время жизни ресурсов;
- `unsafe`-инварианты и границы вызовов нативного кода;
- блокирующая работа внутри async-контекста;
- mutex/lock scope, порядок захвата блокировок, deadlock и race conditions.

### Vue и TypeScript

- type safety без необоснованного `any` и небезопасных assertions;
- корректное использование `ref`, `reactive`, `computed` и props/events;
- очистка listeners, timers и других ресурсов в lifecycle hooks;
- stale async results, конкурирующие запросы и мутации общего состояния;
- состояния loading/success/error/cancel/retry и доступность элементов
  управления.

### Tauri и границы слоёв

- совместимость IPC-контрактов Rust/TypeScript и корректная сериализация;
- валидация входных данных на доверенной backend-границе;
- отсутствие блокирующих операций в Tauri commands и async runtime;
- согласованность изменений command/event DTO со всеми consumers.

### Общие риски

- соответствие существующей архитектуре и source of truth;
- безопасность входных данных, файловых путей, URL и внешних команд;
- отсутствие секретов в логах, ошибках и диагностических артефактах;
- понятные пользовательские ошибки и достаточная диагностика без раскрытия
  чувствительных данных;
- дублирование логики, неочевидное усложнение и измеримый риск деградации
  производительности.

Принятая модель хранения секретов не пересматривается в каждой локальной
задаче, если она не входит в scope. Однако открытое логирование API keys,
access tokens, паролей и других секретов запрещено независимо от scope.

## Формат verdict

````markdown
# Code review — YYYY-MM-DD

## Scope

- Task: `tasks/NNN.md`
- Baseline: `<commit>`
- Проверенный diff: `<paths или range>`

## Findings

### [CRITICAL|MAJOR|MINOR] Краткое название

- Файл: `path/to/file:line`
- Проблема: наблюдаемое несоответствие или дефект
- Риск: конкретное последствие
- Исправление: минимальная ожидаемая корректировка

## Проверки

- `<команда или ручной сценарий>` — passed/failed/not run с причиной

## Verdict

- `accepted` или `changes required`
- Краткое обоснование и следующий task при наличии замечаний
````

Если findings отсутствуют, это указывается явно; пустой раздел не считается
доказательством корректности. Предложения по оптимизации отделяются от дефектов
и не блокируют приёмку без измеримого риска или нарушенного требования.
