# Ручные тест-кейсы

Норматив формирования **ручных** тест-кейсов для функционала, затронутого
roadmap-этапом или группой коммитов. Применяется перед релизом или после
переписи истории, когда автотесты зелёные, но нужно подтвердить поведение в
реальных интеграциях (VTube Studio, Telegram/Silero, Piper, доп-окна).

Это дополнение к [AI-assisted workflow](./ai-workflow.md): автотесты проверяют
контракты и модули, ручные кейсы — то, что требует запущенного приложения и
внешних сервисов.

## Когда писать

- Перед релизом: по диапазону от последнего тега до HEAD.
- После переписи истории: по затронутым roadmap-трекам (дерево не меняется,
  но это повод зафиксировать, что именно проверять).
- Перед приёмкой крупного user-visible этапа.

Не пишутся для: чистого рефакторинга без изменения поведения, правок
документации и конфигурации сборки без runtime-эффекта — их покрывают
автотесты и `check-docs.ps1`.

## Принципы

1. **Группировка по user-visible эффекту, не по коммитам.** Один roadmap-трек
   (напр. ROADMAP-060) — одна группа, даже если он разложен на P0/P1/P2.
2. **Приоритет по видимости.** 🔴 P0 — user-visible, обязательно; 🟡 P1 —
   нишевое/скрытое; ⚪ P2 — архитектура, проверяется косвенно (логи/автотесты).
3. **Каждый кейс = действие + ожидание + регрессия.** Шаги воспроизведения,
   явный ожидаемый результат (✅) и маркер «что считается багом» (❌).
4. **Факт из кода, не догадка.** Имена полей настроек, кнопок, команд, режимов
   берутся из `git show` / roadmap-документов / исходников, а не по памяти.
5. **Разделение manual и автотестов.** Контракты IPC, parity-gate, clippy —
   это автотесты; ручной кейс для них только отмечает, что они зелёные, и
   указывает команду.
6. **Готовый к копированию чеклист** в конце документа для прогона.

## Источники для кейсов

- `docs/roadmap/completed/*.md`, `docs/roadmap/active/*.md` — что входило в трек.
- `git show <sha>` и `git log <range> --name-only` — реальные изменения.
- Изменённые исходники (панели Vue, команды Rust, поля `settings.json`/DTO).

Для диапазона удобно сначала собрать материал по трекам (факты: поля, кнопки,
сценарии), а потом превратить его в кейсы — не наоборот.

## Формат

Сам кейс-документ живёт в `.work/testcase/` (gitignored, рабочий артефакт
сессии) и строится по [шаблону](./templates/test-cases.md). В `docs/`
хранится только этот норматив и шаблон.

Имя файла: `YYYY-MM-DD-manual-testcases.md`, где дата — день формирования.
Если имя уже занято в `.work/testcase/`, добавляется суффикс-нумерация перед
расширением: `YYYY-MM-DD-manual-testcases-2.md`, `-3.md` и т.д.
Документируйте в шапке диапазон ревизий (от тега до HEAD), чтобы различать
прогоны разных дат.
