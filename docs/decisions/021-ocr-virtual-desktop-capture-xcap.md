# DECISION-021 — Захват виртуального рабочего стола через xcap

**Статус:** `accepted`
**Связанный roadmap:** [ROADMAP-088](../roadmap/active/088-one-shot-screen-ocr.md)

## Контекст

One-shot OCR требует один снимок всего виртуального рабочего стола Windows
(мультимонитор, отрицательные координаты мониторов, физические пиксели при
любом DPI) до показа любого UI выделения — паттерн LunaTranslator: кадр
делается первым, область вырезается из сохранённого снимка, поэтому overlay
никогда не попадает в распознавание. В дереве проекта capture-зависимости не
было.

## Решение

Используется crate `xcap` (MIT, ~0.9): перечисление мониторов с их
виртуальными координатами, по-мониторный захват и склейка в один кадр
виртуального стола — геометрия, нормализация/кламп прямоугольника и кроп
реализованы чистыми функциями, тестируемыми без реальных мониторов
(`src-tauri/src/ocr/capture.rs`).

Отклонённые альтернативы:

- сырой DXGI duplication через `windows`-crate: без новой зависимости, но
  ~сотни строк unsafe COM-кода, которые пришлось бы владеть и тестировать;
- `screenshots`/`scap`: сопоставимая функциональность при менее активной
  поддержке; выбор между обёртками сводится к зрелости, у `xcap` она выше.

## Последствия

- Один новый cross-platform dependency; Windows-путь идёт через нативный
  захват xcap, приложение не владеет COM-кодом.
- Кроп идёт из сохранённого кадра, поэтому UI выделения (когда появится)
  не обязан участвовать в захвате и может быть исключён из OBS-захвата
  (`set_window_exclude_from_capture`, паттерн soundpanel).
- Условие пересмотра: подтверждённый дефект xcap на целевых конфигурациях
  (мультимонитор с отрицательными координатами, масштабирование DPI) — тогда
  замена на прямой DXGI не меняет контракт модуля (`capture_virtual_desktop`
  возвращает геометрию + кадр).
